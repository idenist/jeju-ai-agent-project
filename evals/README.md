> **프로젝트 단계:** 기존 V0 동작 검증(16개 자동 테스트) → **실제 LLM 정량 평가(이 폴더)** → 실패 분석 → V1 설계·고도화 → 동일 조건 재평가.
>
> 평가 기준 코드: `seunghyuk` 브랜치의 커밋 `f87481d65ccffbbc10d5c083168cc59c6ca7768e`(2026-11-07). 데이터와 핵심 Python 파일의 Git blob 해시는 `manifest.json`에 고정했습니다.

## 1. 무엇을 평가하는가?

현재 Agent는 서울가락시장 경매가격 CSV와 사용자 보관 조건으로 손익분기를 계산하는 Tool Calling 베이스라인입니다. **미래 가격 예측, 출하량 연동, 과거 다수 구간 시뮬레이션은 아직 없습니다.** 해당 기능을 V0 평가의 실패로 세지 않습니다.

총 **30개 시나리오, 33개 대화 턴**을 준비했습니다.

| 범주 | 문항 | 검증 내용 |
|---|---:|---|
| 출하 손익 비교 | 8 | 입력 조건 추출, 계산 도구 호출, 정확한 금액 |
| 경락가격 조회 | 4 | 조건 일치·결측 코드·조회 불가 |
| 사용자 미래 가격 가정 | 5 | 시나리오 차액, 예측과 가정 구분 |
| 정보 누락 | 6 | 필수 조건 확인, 임의의 손익 계산 방지 |
| 유효하지 않은 입력 | 4 | 감량률 100%, 물량 0, 보관 0일, 음수 보관비 |
| 다중 턴 | 3 | 앞선 조건 유지, 조건 보완, 가정가격 재질문 |
| **합계** | **30** | **총 33개 턴** |

`dataset.jsonl`은 **개발용(dev) 20개**와 **고정 비교용(holdout) 10개**로 구성합니다. 새로운 기능을 튜닝할 때는 우선 `dev`를 사용하고, `holdout`은 고도화 전후 비교와 최종 확인에 사용합니다. 평가 기준을 바꾸어야 한다면 기존 파일을 덮어쓰지 말고 새 버전의 평가셋을 만드세요.

## 2. 준비 및 무과금 점검 (Windows CMD)

프로젝트 루트에서 실행하세요. 가상환경이 이미 활성화되어 있다면 Conda 활성화 단계는 생략할 수 있습니다.

```bat
python -m unittest discover -s evals -p "test_*.py" -v

REM 전체 평가 문항·정답 형식 및 V0 코드/CSV 버전 확인 (외부 API 호출 없음)
python evals\evaluate.py --validate --split all
```

`--validate`는 **성능을 측정하지 않습니다.** 평가셋과 V0 버전을 확인하는 사전 점검입니다. 실행 결과에 `V0 일치`가 나와야 현재 베이스라인의 성능을 측정하는 것입니다.

## 3. 실제 OpenAI API 평가

프로젝트 루트 `.env`에 `OPENAI_API_KEY`와 `OPENAI_MODEL`을 설정하세요. 이미 Agent를 성공적으로 실행했다면 같은 설정을 사용합니다. **실제 API 비용이 발생합니다.**

먼저 적은 문항으로 실행하세요.

```bat
REM 개발셋의 3문항으로 평가 파이프라인 확인
python evals\evaluate.py --live --split dev --limit 3 --out-dir evals\results\v0_smoke
```

오류 없이 실행되면 전체 V0의 성능을 측정합니다.

```bat
REM 30개 문항 · 33개 대화 턴 · 1회 평가
python evals\evaluate.py --live --split all --out-dir evals\results\v0_all
```

반복 실험이 필요하면 `--repeats 2` 또는 `--repeats 3`을 추가합니다. 하지만 API 호출 비용이 반복 횟수에 비례해 증가할 수 있으므로 처음부터 무조건 반복하지는 마세요. `--case-id EVAL-013`으로 특정 문항만 확인할 수도 있습니다(기본 split이 dev이므로 holdout 문항은 `--split all` 또는 `--split holdout` 필요).

요금이 확실할 때만 `--input-usd-per-million`, `--output-usd-per-million`을 직접 지정해 참고용 비용을 계산할 수 있습니다. 미지정 시 비용은 **측정 불가(`null`)**로 남깁니다. 토큰 사용량은 API 응답에서 기록합니다.

### 생성 결과

`evals/results/v0_all/`에 다음 파일이 생성됩니다.

- `metadata.json`: 모델, 실행 시각, 데이터셋 해시, V0 코드·CSV 버전
- `summary.json`: 전체/범주별 통과율, 도구 선택, 인수 추출, 수치 일치, 시간·토큰
- `cases.jsonl`: 문항별 질문·답변, 도구 이름·인수·결과, 실패 원인(API 키는 저장하지 않음)

`evals/results/`는 `.gitignore`로 커밋 대상에서 제외합니다. 발표 자료에 사용할 결과는 직접 검토하고 필요한 요약만 별도로 보관하세요.

## 4. 채점 기준: 같은 숫자를 출력했어도 도구가 틀리면 실패

| 기준 | 자동 판정 방식 | 해석상 주의 |
|---|---|---|
| 도구 선택 | `get_market_price` 또는 `compare_shipping` 필요 여부 확인 | `compare_shipping`은 자체적으로 가격 조회 가능. 불필요한 중복 조회를 필수 실패로 간주하지 않음 |
| 인수 추출 | 종류·등급·규격·물량·보관비·감량률 등 구조화 인수와 정답 비교 | 누락·잘못된 단위 변환은 실패 |
| 도구 숫자 | 실제 Python 함수 반환 JSON과 고정 정답 비교 | 정답은 기존 Agent 함수가 아닌 별도 CSV 계산으로 생성 |
| 최종 숫자 | 보고서의 **각 필드 라벨과 숫자**를 고정 정답과 비교 | 답변 어딘가에 우연히 같은 숫자만 있어도 통과하지 않음 |
| 정보 누락 | 임의 손익 계산 없이 누락 조건을 하나 이상 확인 | 누락 조건을 **전부** 한 번에 확인했는지는 별도 지표로 기록 |
| 잘못된 입력 | 올바르지 않은 입력으로 계산 결과를 확정하지 않는지 | 일부 자연어 판정은 정규식 기반이며 수동 검토 필요 |
| 근거 없는 단정 | 위험 표현 정규식으로 **검토 후보**만 표시 | 정식 '환각률'로 사용하면 안 됨. 사람이 확인해야 함 |

**핵심:** 성공적으로 도구를 호출했는지, 파라미터가 맞는지, 계산값이 맞는지를 **각각 다른 분모**로 계산합니다. 전체 문항 통과율은 모든 기대 조건을 충족한 문항의 비율이며, 다중 턴 문항은 한 턴이라도 실패하면 해당 문항 실패입니다.

입력 정보가 부족한데 LLM이 우선 가격 조회를 했다면 전체 실패로 단정하지 않고 `premature_price_lookup_in_missing_questions`로 따로 기록합니다. 정답이 없는 조건을 임의로 넣어 최종 손익 계산을 하면 실패합니다.

**평가 한계:** 출하 실효성, 미래 가격의 예측 정확도, 사용자 만족도는 측정하지 않습니다. 평가 문항이 30개라 통계적 신뢰구간이나 실제 운영 성능을 단정할 수 없습니다. 금지 주장 감지 등 자연어 평가는 규칙 기반이므로 `cases.jsonl`을 읽고 실패·위험 사례를 수동 검토해야 합니다.

## 5. 고도화 후 V0와 V1 비교

**고정해야 할 것:** 같은 평가 질문·정답, **같은 경락가격 CSV**, 같은 OpenAI 모델, 동일한 평가 반복 횟수. 코드만 V1로 변경하고, 이 평가 스크립트의 채점 규칙은 바꾸지 않습니다.

**출력 계약도 확인하세요.** 현재 수치 평가기는 베이스라인의 보고서 항목명(예: `지연 출하 손익분기 단가:`)을 이용해 정확한 숫자를 읽습니다. V1에서 사용자 보고서의 항목명까지 바꾸면 올바른 숫자라도 이 평가에서 실패할 수 있으므로, V0/V1 비교 시 핵심 수치 보고서 계약을 동일하게 유지해야 합니다. UI나 문장 스타일만 바꾸는 실험은 별도로 평가하세요.

```bat
REM V1 구현을 완료한 뒤 실행. 현재 V0 코드와 달라도 비교 평가할 수 있도록 허용
python evals\evaluate.py --live --split all --allow-version-mismatch --out-dir evals\results\v1_all

REM 동일 평가 문항과 모델인지 검사하고 차이 계산
python evals\compare.py evals\results\v0_all evals\results\v1_all --output evals\results\v0_v1_comparison.json
```

`compare.py`는 **데이터셋 해시, 문항·반복 수, 모델 ID, 입력 CSV 해시가 다르면 비교를 거부**합니다. 명시적으로 `--allow-different-model`을 쓰면 모델이 다른 결과도 보여 주지만, 이 경우 성능 차이가 Agent 구조에서 발생한 것이라고 주장할 수 없습니다.

V1이 과거 다수 기간 시뮬레이션처럼 **V0에 없던 기능**을 구현했다면, 해당 기능은 **별도 신규 기능 평가셋**에서 측정하세요. V0에 그 기능이 없다는 이유로 기존 기능 성능 비교를 왜곡하지 않습니다.

## 6. 평가 후 반드시 확인할 항목

1. `summary.json`에서 도구 선택·인수 추출·수치 정확도 중 가장 큰 실패 원인을 확인합니다.
2. `cases.jsonl`에서 실제 실패한 **질문, 전달된 인수, Python 도구 반환값, 최종 응답**을 확인합니다.
3. 반복 평가 시 같은 질문에서 결과가 달라지는지 점검합니다.
4. V1 기능은 발견된 실패 원인과 연결해 설계하고, 새 기술 도입 자체를 성과로 평가하지 않습니다.
5. 본인이 코드와 평가 기준을 직접 설명할 수 있을 때 V1 구현으로 넘어갑니다.

**다음 개발 단계:** V0 전체 평가 실행 → 실패 사례 표 정리 → V1 기능·기술 선정 → 구현 → 같은 조건에서 재평가.
