# V1 신규 기능 평가셋 — 설계 및 고정본

> **현재 상태: 평가셋과 골드 정답만 준비. V1 Agent 구현과 실제 API 성능 평가는 수행하지 않았습니다.**
>
> 기준일: 2026-11-07 / V0 고정 커밋: `f87481d65ccffbbc10d5c083168cc59c6ca7768e` / 기준 CSV: `data/processed/daily_prices.csv`

## 1. 목적과 평가 범위

V0의 **기존 30개 문항(33턴)**은 고치지 않고 기존 기능의 회귀 평가에 사용합니다. 이 폴더는 V1에서 새로 도입하는 **의사결정 분석 기능**을 별도로 평가합니다. 두 평가를 합쳐 단일 정확도로 보고하지 않습니다.

| 범주 | 문항 | 핵심 검증 |
|---|---:|---|
| 과거 7일 가상 손익 분석 | 8 | 정확히 7일 차이의 가격 날짜쌍, 동일 규격, 양 끝 거래건수 필터, 구간별 가상 손익 |
| 3·7·14일 비교 | 4 | 기간별 **누적** 감량률 구분, 보관비 반영, 누락 시 추가 질문 |
| 민감도 분석 | 4 | 보관비×감량률 조합별 단가와 상승률, 증가 방향 |
| 근거 품질·자료 부재 | 4 | 저표본 제외, 과거 관측일 경과, 유효 구간 0개, 사용자가 모르는 규격 확인 |
| **합계** | **20** | dev 14개 / holdout 6개, 단일 턴 20개 |

**V1 기능 ID:** `V1-F01` 과거 구간 시뮬레이션, `V1-F02` 근거 품질 검증, `V1-F03` 기간 비교, `V1-F04` 민감도. 품종 분류 확인은 `V1-F05` 관련 문제를 함께 포함합니다.

## 2. 파일 구성

- `dataset.jsonl`: 질문, 예상 입력, 결과 골드, 응답 수용 조건을 가진 **20개 평가 문항**. `V1-EVAL-001`~`020`.
- `manifest.json`: 데이터셋 버전·SHA-256, 근거 가격 CSV Git blob SHA, 기준일, 문항 분포.
- `verify_dataset.py`: **외부 API를 호출하지 않는 정합성 검사**. JSON 형식·문항 수·해시·분류·골드 숫자·가격자료 버전을 점검합니다. 실제 Agent를 평가하는 실행기는 아닙니다.

CSV 기반 골드는 V1 생산 코드와 독립적으로, **`total_amount_krw / total_kg`를 날짜마다 새로 계산**하여 생성했습니다. 출력 반올림은 금액 정수 원, 단가 소수 둘째 자리(`ROUND_HALF_UP`)이고, 최소 필요 정수 단가는 `ROUND_CEILING`을 사용합니다. 중간 계산은 반올림하지 않습니다.

## 3. 주요 규칙 (평가 전 고정)

1. 시장 `110001`(서울가락), 경매, 포장 종류 `상자`, **동일 품종·등급·크기·포장중량** 거래만 조회합니다.
2. 과거 `t`와 달력상 정확히 `t+7일`에 거래가 모두 있을 때만 날짜쌍을 인정합니다. 휴장일을 건너뛰거나 가격을 보간하지 않습니다.
3. 양 끝 날짜의 거래건수가 각각 **5건 이상**인 구간을 기본 분석에 포함합니다. 제외 건수도 출력합니다. `5건`은 개발용 필터이며 통계적 신뢰성 보장이 아닙니다.
4. 날짜쌍마다 `Q×(1−r/100)×P(t+7) − 7×C − Q×P(t)`로 가상 차액을 구합니다. 과거 모든 구간에 최신 가격을 대입하지 않습니다.
5. 3·7·14일의 `loss_percent`는 **각 기간 전체의 누적 감량률**로서 서로 독립 입력입니다. 값이 없으면 다른 기간 값을 전용하지 않고 질문합니다.
6. 손익분기 단가는 `(Q×현재 기준단가 + 지연일수×하루 보관비) / [Q×(1−누적 감량률/100)]`입니다.
7. `as_of_date`는 **포함하는 조회 상한**입니다. 이후 데이터를 절대로 사용하지 않습니다.
8. `analysis_date`는 실제 API 실행일이 아니라 평가를 위해 **2026-11-07로 고정된 외부 환경 값**입니다. 최신 관측일부터 3일 이상 경과하면 경고합니다.
9. `min_transactions_per_day=5` 등 **기본 정책값과 평가 기준일은 사용자 발화에서 추출한 값이 아닌 시스템 주입값**으로 취급합니다. LLM 입력 추출 정확도 채점 시 기본값을 사용자 발화에서 추출하라고 요구하지 않습니다.
10. `미상`은 원본 데이터의 결측 표기이지, 사용자가 자기 등급·크기를 모를 때 자동 지정하는 값이 아닙니다.
11. **과거 유리한 구간의 비율을 미래 이익 확률로 말하지 않습니다.** 동일 재고의 실제 보관 재판매가 아니며 구간이 중첩됩니다. 품질 `descriptive_only`는 통계적 신뢰도를 뜻하지 않습니다.

## 4. 데이터셋 구조 및 채점 계획

문항은 `id`, `split`, `category`, `description`, `turns[]`를 가집니다. 각 턴의 `expected`에는 다음이 있습니다.

- `action`: `historical`, `no_data`, `options`, `sensitivity`, `quality`, `ask` 중 하나.
- `primary_tool`: **목표 인터페이스** 이름(`analyze_historical_delays`, `compare_delay_options`, `analyze_sensitivity`, `assess_evidence_quality`). 도구명은 제안된 명세이며 현재 코드에 아직 구현되지 않았습니다. 품질 결과를 내부 도구에서 함께 계산하는 동등한 설계는 V1 구현 전 평가 계약에 명시적으로 매핑해야 합니다.
- `args`: 요구된 데이터 계약상의 정형 인수. `analysis_date`, 기본 필터 등은 시스템값입니다. `ask`의 `null`은 **없는 값**이지 임의 가정이 아닙니다.
- `gold`: 독립 계산 숫자·참조 구간·자료 품질 상태·경고. 숫자 대부분 문자열로 표기하여 실수 반올림 오류를 피합니다. 가격 출처 `csv`와 `user`는 분리됩니다.
- `missing`, `required_behavior`, `safety_checks`, `grading`: 누락 재질문, 금지 동작, 결과에 반드시 나타나야 하는 설명.

**채점 분리:** (A) 실제 도구와 인수 선택, (B) 도구가 반환한 정형 숫자, (C) 최종 사용자 답변의 핵심 수치, (D) 정책·근거 경고는 따로 평가합니다. 숫자의 기대값이 있다는 이유만으로 모든 수치를 매번 사용자 답변에 나열하도록 강요하지 않고, `grading.final_answer_required`의 의미적 요구를 확인합니다. 특히 근거 없는 확정 추천·미래 확률은 결함입니다.

**예시:** `V1-EVAL-001`은 후보 21구간, 저표본 1구간 제외, 유효 20구간, 가상 이익 7·손실 13구간을 기대합니다. `V1-EVAL-004`는 2026-10-07→10-14의 가격 상승에도 **가상 차액이 약 -173,791원**임을 검사합니다. 데이터가 다르면 값이 달라질 수 있으므로 변경된 CSV로 기존 골드를 평가하지 않습니다.

## 5. 지금 진행할 검증 (API 호출 없음)

프로젝트 루트에서 CMD로 실행합니다.

```bat
python evals\v1\verify_dataset.py
```

이 검사는 **골드셋에 오류가 없는지** 확인합니다. Agent V1 성능을 측정하지 않습니다. 기존 V0 `evals\evaluate.py`는 `expected.action`이 다른 V1 신규 기능 문항을 아직 지원하지 않으므로 이 파일로 V1을 `--live` 실행하면 안 됩니다.

## 6. V1 완성 후의 평가 절차

1. V1의 기능 구현과 독립 단위 테스트 완료.
2. 별도 V1 신규 기능 평가 실행기에 `dataset.jsonl`의 계약을 연결하고, 평가 기준을 임의로 바꾸지 않습니다.
3. `dev` 14개로 실행·채점 파이프라인 확인 후, **최종 시점에 `holdout` 6개를 한 번만** 사용합니다.
4. 기존 V0 30문항을 V1에서 **동일 모델·데이터·평가 기준**으로 다시 실행해 회귀 성능을 확인합니다.
5. V1 신규 20문항 결과는 신규 기능 성능으로 **별도 보고**합니다. 두 결과를 합산해 1개의 정확도 수치로 만들지 않습니다.
6. 질문·정답을 공개 저장소에 커밋하면 의미상 holdout도 접근 가능해진다는 점에 유의합니다. **개발 중 정답을 보고 튜닝하면 holdout으로서의 독립성은 상실**됩니다. 최종 신뢰성 검증을 원한다면 별도의 미공개 최종 평가 문항을 추가합니다.

**정답 변경 정책:** V1 구현 결과에 맞춰 골드를 고치지 않습니다. 잘못된 근거 데이터나 계산 오류가 확인되면 문항 ID, 사유, 이전/수정 값을 기록하고 **새 데이터셋 버전**을 만듭니다.
