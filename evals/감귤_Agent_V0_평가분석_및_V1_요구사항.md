## 2. 실패 사례 EVAL-007 — 확인된 사실

**입력:**

> 하우스감귤 특등급 중과 5kg 상자 800kg을 3일 보관할 때 하루 추가 비용 6,000원, 전체 감량 1%면 즉시 출하와 비교해 줘.

**기대:** `compare_shipping` 호출, `variety=하우스감귤`, `grade=특`, `size=중`, `package_kg=5`, `quantity_kg=800`, `delay_days=3`, `daily_storage_cost=6000`, `loss_percent=1`.

**실제:** 모델이 도구를 하나도 호출하지 않고 `하우스감귤`을 재배 방식이라 해석하여 품종을 다시 질문함. 이로 인해 도구 선택·인수 추출·수치 출력 점수가 **하나의 원인으로 동시에 하락**했다. 서로 독립적인 세 가지 오류로 집계해서는 안 된다.

**반증/교차 확인:**

- EVAL-011은 **동일한 `하우스감귤·특·중·5kg` 조건의 가격 조회**이며 `get_market_price`를 정상 호출해 통과했다. 따라서 '하우스감귤을 전혀 모르는 모델'이라는 설명은 맞지 않다.
- 경매 원천정보 소분류 `05`에 대응하는 표준 라벨은 실제로 `하우스감귤`이다. 일상적 식물학 분류와 **해당 데이터의 상품 분류**를 구분해야 한다.
- V0 Python `compare_shipping` 도구에 기대 인수를 **직접** 전달하면 정상 계산됨. 최근 관측일 2026-11-03, 관측 단가 **2,815.77원/kg**(9건), 즉시 출하 가정 매출 **2,252,616원**, 3일 보관 뒤 물량 **792kg**, 추가 보관비 **18,000원**, 손익분기 **2,866.94원/kg**, 정수 단가 **2,867원/kg 이상**, 필요 상승률 **1.82%**.

**가능성이 높은 원인(가설):** 모델이 의사결정 질문에서는 일반적인 농업 용어 의미에 근거한 추가 확인을 우선했고, **데이터셋의 허용 품종값을 참조하는 명시적 검증·정규화 단계가 없었다.** 단 한 번의 실패로 원인을 확정할 수는 없다.

### 변경 전 재현 실험 — 아직 미수행

기존 V0 코드를 변경하지 않고 EVAL-007을 5회 독립 반복한다.

```bat
python evals\evaluate.py --live --split dev --case-id EVAL-007 --repeats 5 --out-dir evals\results\v0_e007_repeat
```

이 명령은 **실제 OpenAI API 과금**을 유발할 수 있다. 반환된 `cases.jsonl`에서 각 시행의 도구 호출 여부, 인수, 응답을 확인한다. **5회 결과를 얻기 전에는 일회성 문제인지 재현 가능한 문제인지 단정하지 않는다.**

## 3. 추가로 발견한 취약점(평가 실패와 별개)

1. **`미상`의 의미 혼동:** EVAL-019 및 EVAL-020의 추가 질문은 `미상`을 사용자가 임의로 선택할 수 있는 실제 등급·크기처럼 안내한다. 원본에서 `미상`은 데이터 결측 표시이므로 사용자 규격의 미확인 상태와 구분해야 한다.
2. **자료 시점/근거 표현:** 현재 시장가격은 2026-11-03까지의 관측치다. 실제 실시간 경락가·농가 수취가격으로 인식되지 않도록 관측일과 데이터 신선도를 표시해야 한다.
3. **조건부 판단 표현:** 미래 가격을 사용자가 가정한 경우, 그 가정 안에서의 유불리는 명확히 결론 낼 수 있다. 현재 고정 보고서의 '실제 우열 확정 불가'와 함께 제시할 때 혼동을 줄여야 한다.
4. **평가 문항 편중:** 실제 가격 조회·손익분기 중심이고, 경계 사례(동의어·상품 분류 충돌·날짜 부재·모순된 입력) 및 신뢰성 높은 다중 구간 분석 평가가 부족하다.

## 4. V1 요구사항 — 반드시 구현할 것과 후순위 구분

### V1-R01. 시장 데이터 분류체계 우선 검증 — 필수 / 최우선

- `daily_prices.csv` 또는 전처리 코드에서 제공하는 **표준 품종·등급·크기값**을 단일 출처로 관리한다.
- `하우스감귤`은 공식 데이터 라벨로 인정한다. 근거 없이 일반적인 농업 분류로 대체하거나 추가 품종을 생성하지 않는다.
- 구어 별칭은 명확하게 1:1 대응되는 경우에만 정규화한다. 다의적이면 질문한다.
- `사용자가 모름`과 `원본 결측값(미상)`은 별개 상태로 관리한다. 미확인 상품 규격을 `미상` 데이터와 자동 연결하지 않는다.
- **완료 조건:** EVAL-007과 유사한 `하우스감귤` 출하 비교 질문에서 정확한 규격으로 도구 호출; 데이터 사전에 없는 품종은 추측 없이 확인; 정상 조생귤 질문 회귀 통과.

### V1-R02. 입력 계약과 유효성 검사 강화 — 필수

- 질문 해석으로 얻은 값과 계산 도구 입력 사이에 Pydantic 등의 **정형 검증 계층**을 둔다. 현재 Python 계산 엔진의 수치 범위 검사는 유지한다.
- 필수값 누락·값 범위 위반·모순된 입력을 구분하여 처리한다. 명확한 값만 도구로 전달한다.
- 검증 규칙은 모델 지시문뿐 아니라 Python 코드로 강제한다.
- **완료 조건:** 0kg, 0일, 음수 보관비, 감량률 100%, 원본 `미상` 혼동 케이스를 결정적으로 처리한다. 기존 16개 테스트 및 신규 검증 테스트 통과.

### V1-R03. 과거 N일 지연 출하 가상 시뮬레이션 — 서비스 차별화 핵심

- 기존 손익분기 계산에 더해, **동일 시장·품종·등급·크기·포장중량**의 정확히 N일 떨어진 관측가격 쌍으로 보관 가상 손익을 계산한다. 기본 후보 기간은 3·7·14일.
- 각 날짜쌍에 사용자가 입력한 물량·보관비·기간별 누적 감량률을 적용한다.
- **결과:** 관측 가능한 구간 수, 보관이 유리했던 사례 수/불리했던 사례 수, 손익 범위, 데이터 품질·표본 수.
- 양 끝의 거래가 부족한 구간을 별도 표시하거나 품질 기준에 따라 제외한다. 겹치는 구간은 독립 표본처럼 해석하지 않는다.
- **엄격한 해석 제한:** 같은 감귤을 실제로 저장·재판매한 실험이 아니라 시장 집계가격을 사용한 반사실적 시뮬레이션. 승률을 **미래 이익 확률**로 표시하지 않는다.
- **완료 조건:** 작은 합성 CSV에서 기준값을 수작업·독립 수식으로 검증; 거래가 부족한 구간·동일 규격 미존재 시 안전하게 설명; 가격 변동과 손익 차이를 정확히 구분.

### V1-R04. 근거·불확실성 표시와 조건부 결론 — 필수

- 분석 출력에 데이터 출처, 관측일, 조회 조건, 거래건수 및 사용자가 가정한 비용·감량률을 명시한다.
- 사용자의 미래 가정가격 시나리오에는 **'이 가격이라면 지연/즉시 출하가 금액상 유리'**라는 조건부 결론과, **'실제 미래 가격을 예측하지 않음'**을 구분해서 쓴다.
- 데이터 없는 조건을 다른 규격 평균으로 조용히 대체하지 않는다.
- **완료 조건:** 금액은 Python 도구 결과와 일치하고, 출처·가정·결측 경고가 출력에 포함된다.

### V1-R05. 비교 가능한 평가 유지 — 필수

- V0의 코드·데이터·평가셋·원본 출력은 변경 없이 보존한다.
- 기존 30개 평가 질문은 **회귀 성능 측정용**으로 사용한다. EVAL-007의 회복 여부를 별도 확인한다.
- 도메인 분류 충돌·원본 `미상`·모호한 표현·신규 시뮬레이션을 검증할 **추가 개발용 평가셋**을 만든다.
- 신규 기능의 정확도는 Python 독립 계산/테스트로 검증하고, LLM 도구 선택·입력 추출은 실제 API로 평가한다.
- **완료 조건:** 동일 모델·동일 데이터·평가셋에서 V0/V1 도구 선택, 파라미터 추출, 수치 출력, 안전 대응, 응답시간/토큰을 비교. 평가 결과에 실패 로그와 재현 조건 포함.

### 후순위 — V1에서 자동 도입하지 않음

- **LangGraph:** 현재의 조건 누락·라우팅·분기 복잡도가 실제로 증가하여 상태 그래프가 필요해질 경우에만 도입. 그래프만 그리는 작업은 제외.
- **RAG·MCP·A2A·가격예측 모델:** 팀 통합 요구와 자료 범위가 확인되기 전에는 적용하지 않음.
- **제주 출하량 연계:** 가격 데이터와 시점/품종 대응이 아직 불일치하므로 사전 검증 후 별도 기능으로 설계.

## 6. 비교 평가 원칙 및 목표

- **기존 기능 회귀:** 기존 16개 테스트 전부 통과, V0의 30개 사례에서 성능 저하가 없는지 확인. 한 번의 30/30만으로 안정성 개선을 단정하지 않는다.
- **타깃 오류 개선:** EVAL-007 및 표현을 바꾼 유사 사례를 독립 반복 평가하고 `compare_shipping` 호출과 정확한 인수 추출을 확인.
- **신규 기능:** 역사적 손익 시뮬레이션의 계산 정확성/표본·결측 처리와 사용자 설명 정확도를 **별도 평가셋**으로 검증한다. 이를 V0의 기존 성공률에 단순 합산하지 않는다.
- **공정성:** 동일 모델(`gpt-6-luna`), 동일 가격 CSV, 동일 평가 조건을 유지한다. SDK/프롬프트/코드 변경은 V1 변경 이력에 명시한다.
- **주의:** 이미 노출된 `holdout` 질문은 엄밀한 미공개 검증용으로 재사용하지 않는다. 신규 블라인드 평가셋은 V1 개발 과정에서 열람·튜닝하지 않는다.
- **성능 주장:** 개선율은 점 추정만이 아니라 반복 실행의 성공 횟수와 실패 사례까지 제시한다. 작은 표본의 우연한 성공을 일반화하지 않는다.
