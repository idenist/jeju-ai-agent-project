# 05. 테스트 및 평가

> **적용 대상:** 제주 감귤 출하 의사결정 AI Agent, `integration/agents` 브랜치  
> **문서 작성 기준:** `65175656e637d576056da76d5915287a2a68a84e` (`6517565`, 2026-11-11)  
> **대상 독자:** 통합 코드를 테스트하거나 팀 인수·발표 자료를 검토하는 팀원  
> **읽는 방법:** 1~3장에서 검증 현황을 이해하고, 4장에서 테스트를 재현한 다음, 5~7장에서 실제 모델과 인수 결과를 확인합니다.

## 1. 프로젝트에서는 무엇을 검증하나요?

이 프로젝트의 검증은 크게 **숫자와 데이터가 올바른가**, **화면과 Agent가 의도대로 연결되는가**, **실제 언어모델도 필요한 도구를 선택하는가**의 세 질문으로 나뉩니다.

한 예로 사용자가 “3,000kg을 7일 보관할 때 필요한 가격을 알려주세요”라고 요청했다고 가정하겠습니다.

1. **계산 테스트:** 물량 3,000kg, 감모 2%, 하루 보관비 20,000원을 입력했을 때 손익분기 단가가 3,109원/kg으로 계산되는지 확인합니다.
2. **통합 테스트:** 자연어 질문이나 조건 카드에서 계산을 실행하더라도 동일한 `calculation_service.py`를 거치는지 확인합니다.
3. **화면 테스트:** 조건을 변경했을 때 화면, PDF, JSON에 같은 결과가 반영되는지 확인합니다.
4. **실제 모델 평가:** 언어모델이 질문을 읽고 `compare_shipment_options` 등의 적절한 도구를 직접 선택하는지 확인합니다.
5. **인수 검증:** 평가 기록과 현재 코드·데이터가 같은 버전인지 확인합니다.

### 1.1 자주 등장하는 용어

| 용어 | 이 프로젝트에서의 의미 |
| --- | --- |

### 2.1 그사이 코드가 어떻게 달라졌나요?

`3aeaf25` 이후 `cb87572`에서 준억님 개선사항을 반영했습니다.

이 변경은 코드와 자동 테스트 추가를 확인한 상태입니다. **최신 코드에서 548개 전체 테스트와 실제 모델 12문항 평가를 통과했는지는 별도로 실행해 확정**해야 합니다.

## 4. Windows CMD에서 재현하기

모든 명령은 **프로젝트 루트 폴더**에서 실행합니다. 예시는 Python 3.13으로 `setup-center.cmd`를 완료하고 `.venv`가 존재하는 환경을 기준으로 합니다.

### 4.1 버전과 작업 상태 확인

```bat
 git branch --show-current
 git rev-parse --short HEAD
 git status --short
```

`integration/agents` 브랜치인지 확인하고, 출력되는 커밋을 결과 기록에 함께 적습니다. 작업 중인 변경사항이 있으면 먼저 별도 커밋 또는 백업으로 보존합니다.

### 4.2 전체 제품 테스트

```bat
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py"
```

성공 시 마지막에 `Ran N tests`와 `OK`가 출력됩니다. 현재 코드에서 예상하는 `N`은 **548**이지만, 실제 개수는 실행 로그를 기준으로 확정합니다.

문제가 발생했을 때 특정 파일만 확인하려면 다음처럼 실행할 수 있습니다.

```bat
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_integration_price_history_followup.py" -v
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_integration_ui_journey.py" -v
```

### 4.3 평가기 테스트

```bat
.\.venv\Scripts\python.exe -m unittest discover -s evals -p "test_*.py"
```

이 검사는 실제 언어모델 호출 없이 평가 프로그램의 동작을 점검합니다. 이전 확인 결과는 14개 통과입니다.

## 5. 실제 모델 E2E 평가

자동 테스트가 통과해도 모델의 도구 선택은 별도로 확인해야 합니다. 이때 [`evaluate_integrated_agent.py`](../scripts/evaluate_integrated_agent.py)가 실제 OpenAI Responses API를 호출합니다.

### 5.1 평가 문항이 다루는 상황

| 문항 | 확인할 사용자 상황 |
| --- | --- |
| INT-01 | 정확한 규격의 과거 7일 가격 조회 |
| INT-02 | 대화 중 7일을 14일로 바꾸며 기존 규격 유지 |
| INT-03 | 사용자가 기존 등급을 취소한 경우 |
| INT-04 | 품종을 통칭 ‘감귤’로 말한 경우 |
| INT-05 | 준비되지 않은 10일 가격 비교 요청 |
| INT-06 | 등급과 크기를 모르는 경우 |
| INT-07 | 과거 가격 조회에서 손익 계산으로 업무 전환 |
| INT-08 | 화면의 직접 조회 이후 자연어 후속 질문 |
| INT-09 | 과거 변동을 미래 판매가격으로 확정해 달라는 요청 |
| INT-10 | 한 질문에서 과거 가격 조회와 손익 비교를 함께 요청 |
| INT-11 | 10kg 포장 표기와 5kg 중량의 충돌 |
| INT-12 | 앞선 규격을 버리고 새로운 조회를 시작하는 요청 |

각 문항에는 기대 도구와 상태, 사용자가 명시한 조건, 불필요한 상태 변경 여부 등이 기록되어 있습니다.

### 5.2 실제로 무엇을 채점하나요?

평가기의 [`score_turn()`](../scripts/evaluate_integrated_agent.py)은 다음 내용을 확인합니다.

1. 기대한 Python 도구를 **모델이 실제 함수 호출로 선택**했는지 확인합니다.
2. 도구가 예상 상태(`OK`, `NEEDS_INPUT` 등)와 핵심 결과값을 반환했는지 확인합니다.
3. 후속 질문에서 조건이 승계·철회됐는지 확인합니다.
4. 기존 손익 시나리오가 예기치 않게 수정됐는지 확인합니다.
5. 가격 조회가 성공한 경우 원천 검증 정보가 존재하는지 확인합니다.
6. 실제 표시 결과가 보고서와 일치하는지 추가 품질 검사를 수행합니다.

모델이 마지막에 그럴듯한 문장을 작성했다는 이유만으로 통과시키는 방식은 아닙니다. 다만 **평가 문항에 명시된 항목만 자동 채점**하므로 수동 기록 검토도 필요합니다.

### 5.3 평가 실행 순서

**실제 API 사용량에 따라 비용이 발생합니다.** `.env`에 `OPENAI_API_KEY`와 평가에 사용할 모델이 설정된 상태에서 실행합니다.

먼저 변경한 입력 처리 사례를 개별 확인할 수 있습니다.

```bat
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --live --case INT-04
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --live --case INT-11
```

다만 두 문항만 통과했다고 전체 평가를 완료한 것은 아닙니다. 최종 전체 평가 명령은 다음과 같습니다.

```bat
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --live --all --repeat 1
```

이 명령은 문항별 새로운 작업공간을 준비하고 **12문항·16턴**을 실행합니다. 사용자 턴 수와 API 요청 수는 같지 않을 수 있습니다. 한 턴 안에서 모델이 도구를 선택하기 위해 여러 번 요청할 수 있기 때문입니다.

### 5.4 실제 모델 평가 결과 읽기

결과는 자동 생성된 폴더에 저장됩니다.

```text
artifacts/
└── integration-e2e/
    └── <평가 실행 시각>/
        ├── metadata.json    # 사용 모델, 평가셋, 코드·데이터 해시
        ├── summary.json     # 전체 통과·실패·사용량 집계
        └── cases.jsonl     # 각 문항·턴의 도구 호출과 상세 채점
```

`summary.json`에서 우선 확인할 항목:

| 필드 | 의미 | 전체 통과 시 기준 |
| --- | --- | --- |
| `planned_runs` | 계획된 문항 실행 수 | 12 |
| `completed_runs` | 완료된 문항 실행 수 | 12 |
| `passed_runs` | 통과한 문항 실행 수 | 12 |
| `complete` | 전체 실행 완료 여부 | `true` |
| `stop_reason` | 중단 사유 | `null` |
| `failure_counts` | 채점 실패 사유별 개수 | 빈 객체 `{}` |
| `usage` | 실제 모델 요청 및 토큰 사용량 | 기록값 확인 |

`cases.jsonl`은 각 문항의 실패 원인과 모델의 실제 도구 입력을 확인할 때 읽습니다. 파일에 질문·모델 호출·상태 정보가 포함되므로 팀 외부로 공유하기 전 내용을 확인합니다.

### 5.5 예전 12/12 통과와 현재 평가의 차이

2026-11-10 전체 평가에서 `gpt-6-luna`가 **12문항·16턴 모두 통과**했습니다. 그 당시에는 다음 두 가지 사용성 문제를 수동 검토에서 발견했습니다.

- **INT-04:** `get_price_history` 도구 선택은 맞았지만 명시한 `특`·`소`를 모델 입력 인수에서 누락했습니다.
- **INT-11:** 포장 중량의 충돌을 선택하지는 않았지만, 안내문에서 10kg와 5kg의 차이를 충분히 설명하지 못했습니다.

이후 최신 코드에는 두 문제의 개선과 회귀 테스트가 들어갔습니다. **이 변경의 실제 모델 효과는 현재 커밋을 대상으로 다시 평가한 결과로 판정**합니다. 기존 평가셋은 과거 비교가 가능하도록 그대로 보존하며, 추가 품질 기준이 필요하면 새 회귀 사례를 별도로 추가합니다.

## 6. 최종 기술 인수 검증

개별 테스트 결과와 실제 모델 평가 결과가 모두 준비되면 [`verify_integration_handoff.py`](../scripts/verify_integration_handoff.py)를 실행합니다.

### 6.1 인수 검증기는 무엇을 확인하나요?

- 전체 E2E 문항과 16턴이 완료·통과했는지
- 실제 모델을 호출했다는 평가 메타데이터가 있는지
- **평가 당시 코드·자료의 SHA-256이 현재 파일과 같은지**
- 동결 가격 원천에서 2,299개 비교행과 4,776개 전체 시도행을 재생성했을 때 내용이 일치하는지
- 통합 Agent의 활성 도구 목록이 검증 당시 계약을 유지하는지
- 전체 제품 테스트·평가기 테스트·평가 사전검증이 통과하는지
- Git 브랜치, 작업트리 상태, 금지된 비밀 파일 추적 여부

검증기는 **기존 E2E 결과를 다시 채점하지 않고**, 기록에 남은 통과·실행·소스 버전 정보를 점검합니다. 따라서 새 코드의 모델 성능을 증명하려면 해당 코드로 실제 모델 평가를 새로 생성해야 합니다.

### 6.2 실행 명령

새로운 E2E 전체 평가 결과를 생성한 뒤에는 다음을 실행합니다.

```bat
.\.venv\Scripts\python.exe -m scripts.verify_integration_handoff --full
```

팀 인수용으로 확정할 때는 코드와 문서가 커밋된 깨끗한 작업트리에서 실행합니다.

```bat
.\.venv\Scripts\python.exe -m scripts.verify_integration_handoff --full --require-clean
```

특정 E2E 증빙 폴더를 직접 지정할 수도 있습니다.

```bat
.\.venv\Scripts\python.exe -m scripts.verify_integration_handoff --full --evidence "artifacts\integration-e2e\평가폴더명"
```

**유의할 점:** 최신 `6517565`에 이전 `3aeaf25`의 모델 평가 증빙만 남아 있다면 `source_hashes_match=false`로 실패할 수 있습니다. 이는 버전 불일치를 정확히 발견한 결과입니다. `--full` 실행 시 전체 자동 테스트는 수행되므로 `tests.status=OK`여도 최종 `status=FAIL`이 나올 수 있습니다.

### 6.3 결과 파일과 판정

```text
artifacts/
└── integration-handoff/
    └── <검증 실행 시각>/
        ├── summary.json    # 최종 판정과 세부 검사 상태
        ├── 검증_1.log       # 제품 전체 자동 테스트
        ├── 검증_2.log       # 평가기 자동 테스트
        └── 검증_3.log       # 통합 평가셋 사전검증
```

판정 예시:

| 값 | 읽는 법 |
| --- | --- |
| `status=PASS` | 요청한 전체 인수 점검이 통과했습니다. |
| `status=PREFLIGHT_PASS` | `--full` 없이 사전 점검을 통과했습니다. 전체 테스트 실행 결과는 아닙니다. |
| `status=FAIL` | `evidence`, `data`, `repository`, `tests`에서 실패한 항목을 확인합니다. |
| `source_hashes_match=true` | 실제 모델 평가 당시 기록한 파일과 현재 파일이 일치합니다. |
| `working_tree_clean=true` | 현재 Git 작업트리에 미커밋 변경이 없습니다. |
| `paid_model_called=false` | **인수 검증 명령 자체**는 새 모델 호출을 수행하지 않았다는 뜻입니다. 과거 E2E는 별도 기록으로 확인합니다. |

현재 검증기 코드는 제품 테스트 수의 **최소 허용값을 543개**로 검사합니다. 신규 코드에서 예상되는 548개가 모두 실행됐는지는 `tests[].test_count`를 별도로 확인해 기록해야 합니다.

## 7. 자동 테스트 이후의 화면 확인

자동 테스트와 실제 모델 평가가 통과해도 발표·팀 인수에서는 사용자가 직접 화면을 따라가며 확인하는 절차가 필요합니다. 다음은 팀원 1명이 로컬 앱에서 재현할 수 있는 확인표입니다.

| 순서 | 실행할 과업 | 확인할 화면 또는 결과 |
| --- | --- | --- |
| 1 | `run-juneok.cmd`로 실행 | 앱이 로컬 주소에서 열리고 데이터 관측기간이 표시됨 |
| 2 | **가상 예시 조건 불러오기** | 3,000kg, 현재 3,000원/kg, 7일 보관 대안이 카드에 표시됨 |
| 3 | **출하 조건 비교** | 최소 정수 손익분기 단가 3,109원/kg 확인 |
| 4 | 감모 2%를 4%로 수정 후 **입력 조건 비교** | 새 조건 기준 최소 정수 단가 3,174원/kg 확인 |
| 5 | **과거 경락가격 직접 조회** | `조생귤 / 특 / 소 / 상자 / 5kg / 7일`의 관측 결과 확인 |
| 6 | 가격 조회 → 손익 비교 → 가격 조회 순서로 전환 | 화면·PDF·비교 JSON에 각각 현재 결과가 들어가는지 확인 |
| 7 | **비교 JSON 내려받기** 후 **비교 파일 확인** | 저장 조건·당시 결과가 읽히고, 복원 시 현재 조건으로 다시 계산되는지 확인 |
| 8 | 포장중량 10kg·5kg 충돌 상황을 자연어로 요청(모델 키 필요) | 두 중량이 표시되고, 정정 후 다음 조회로 이어지는지 확인 |
| 9 | 정산 카드에서 가상 출하 기록과 판매·비용 입력 | 지급액·입금액 검산 및 개인 JSON·PDF 출력 확인 |

직접 화면을 확인한 경우 다음과 같이 결과를 기록합니다.

```text
검토 날짜: YYYY-MM-DD
검토자: (이름)
브랜치/커밋: integration/agents / (git rev-parse --short HEAD 결과)
실행 환경: Windows / Python 버전 / 사용 모델(해당 시)
검토한 시나리오: (표의 순서 번호)
결과: 통과 / 실패 / 미실시
발견한 문제와 재현 방법: (필요시 기록)
증빙 위치: (로컬 로그·캡처 경로)
```

이 기록은 사람의 화면 점검이며 **실제 농가를 대상으로 한 사용성 평가와는 구분**합니다.

## 8. 실패가 발생했을 때 확인 순서

| 증상 | 먼저 확인할 내용 |
| --- | --- |
| `ModuleNotFoundError` 또는 앱 실행 실패 | `.venv` 존재 여부, `setup-center.cmd` 설치 완료 여부, Python 3.13 x64 |
| 일부 자동 테스트 실패 | 실패한 테스트 파일·메서드 이름, 현재 커밋, 오류의 첫 번째 Traceback |
| `--validate`에서 가격 데이터 실패 | 활성 경매 CSV와 동결된 가격쌍 원천의 일치 여부, `VERSION_MISMATCH` 등 오류 사유 |
| 실제 모델 평가에서 도구 선택 실패 | `cases.jsonl`의 `model_tool_arguments`, `failures`, `history_query` |
| E2E 평가가 중단됨 | `summary.json`의 `stop_reason` 및 API 인증·요청 제한 등 오류 |
| 인수 검증에서 `source_hashes_match=false` | `metadata.json`의 `source_sha256`와 현재 코드 차이. 코드가 달라졌다면 해당 버전으로 평가 재실행 |
| `--require-clean` 실패 | `git status --short`로 문서·코드의 미커밋 변경 확인 |
| PDF·JSON 내용이 다름 | 화면에서 마지막으로 실행한 도구, 입력 수정 후 재조회 여부, `current_entries()` 기준 결과 확인 |

## 9. 팀에 전달할 최종 검증 기록 양식

팀에 검증 완료를 공유할 때는 숫자만 전달하기보다 다음 정보를 한 번에 남깁니다.

```text
[통합 Agent 검증 결과]
검증일: YYYY-MM-DD
대상: integration/agents / (정확한 커밋 SHA)
Python/OS: (실행 환경)

제품 자동 테스트: N개 중 N개 통과
평가기 테스트: N개 중 N개 통과
평가셋 사전검증: OK / FAIL
실제 모델: (모델 ID)
실제 모델 E2E: N/12문항, N/16턴 통과
데이터: 가격 비교 2,299행 / 전체 시도 4,776행 검증
소스 SHA-256 일치: true / false
최종 인수 점검: PASS / FAIL
수동 화면 검토: 완료 / 일부 / 미실시

검증 결과 폴더: artifacts/...
잔여 문제: (있으면 기록)
```

### 팀 인수 완료 조건

1. 해당 커밋에서 자동 테스트와 데이터 사전검증이 통과합니다.
2. 실제 모델을 호출한 전체 E2E 기록이 해당 커밋의 코드 해시와 일치합니다.
3. 최종 인수 검증에서 `PASS`가 확인됩니다.
4. 남은 문제, 사용자 화면 검토 결과, 데이터 이용조건 및 팀 승인 상태를 함께 공유합니다.
