## 1. 지금 어디까지 왔나요?

세 팀원의 개별 구현은 `integration/agents`에서 하나의 사용자 화면과 활성 대화 Agent, 공통 계산·데이터 검증 서비스로 연결되어 있습니다. STEP 1~8에서 공통 계약 수립, 계산 경로 통일, 과거 가격 조회 연동, UI 통합, 실제 모델 평가, 기술 인수 검증까지 진행했습니다.

현재는 **새 기능을 계속 추가하기보다, 통합본의 검증을 최신 코드에 맞추고 팀이 유지·운영할 기준을 확정할 시점**입니다.

### 1.1 구현과 검증을 구분한 현재 상태

| 항목 | 현재 확인된 상태 | 다음 행동 |

### 1.2 이 문서의 역할

- **무엇을 먼저 해야 하는지:** 우선순위와 선행 조건을 정합니다.

- **누가 무엇을 결정할지:** 팀 차원의 설계 선택과 승인 사항을 구분합니다.

이미 구현된 기능의 설명은 [01 프로젝트 개요 및 현황](01_프로젝트_개요_및_현황.md), 내부 연결 구조는 [02 시스템 아키텍처](02_시스템_아키텍처.md), 계산·데이터 규칙은 [03 데이터 및 계산 명세](03_데이터_및_계산_명세.md), 실행 방법은 [04 사용자 및 운영 가이드](04_사용자_및_운영_가이드.md), 평가 명령은 [05 테스트 및 평가](05_테스트_및_평가.md)를 기준으로 합니다.

## 3. 1단계 — 최신 통합본 재검증 (P0)

### 3.1 왜 이 작업이 먼저인가요?

STEP 8 인수 검증은 `3aeaf25`의 깨끗한 작업트리에서 `PASS`를 받았습니다. 그 뒤 `cb87572`에서 입력 모순 처리와 JSON 저장 흐름을 바꿨고, 최신 `6517565`에서는 문서 위치도 변경됐습니다.

따라서 **현재 버전의 구현 상태와 과거 검증 기록의 대상 버전이 다릅니다.** 먼저 최신 코드에 대한 새로운 증빙을 만들어야 다음 수정이나 `main` 리뷰의 출발점이 분명해집니다.

### 3.2 수행 순서

**A. 무료 자동 검사**

프로젝트 루트에서 Windows CMD를 사용합니다.

```bat
git branch --show-current
git rev-parse --short HEAD
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py"
.\.venv\Scripts\python.exe -m unittest discover -s evals -p "test_*.py"
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --validate
```

기존에 추가된 5개 테스트가 실제로 발견되는지, 전체 테스트가 끝까지 통과하는지 확인합니다. 오류가 발생하면 해당 기능과 테스트를 우선 수정하고 결과를 다시 기록합니다.

**B. 실제 모델에서 바뀐 두 사례 확인**

먼저 INT-04와 INT-11을 개별 실행하여 도구 선택뿐 아니라 모델이 넘긴 **실제 함수 인수**와 사용자 안내 문장을 살펴봅니다.

```bat
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --live --case INT-04
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --live --case INT-11
```

실제 OpenAI API를 사용하므로 비용이 발생할 수 있습니다. 이 사례가 확인되면 고정 평가셋 전체를 실행합니다.

```bat
.\.venv\Scripts\python.exe -m scripts.evaluate_integrated_agent --live --all --repeat 1
```

**C. 최종 기술 인수 증빙 갱신**

```bat
.\.venv\Scripts\python.exe -m scripts.verify_integration_handoff --full
```

검수용 소스가 확정·커밋되고 작업트리가 깨끗해지면 다음 명령으로 최종 판정합니다.

```bat
.\.venv\Scripts\python.exe -m scripts.verify_integration_handoff --full --require-clean
```

인수 검증기는 실제 모델 평가 기록의 SHA-256을 현재 코드·데이터와 대조합니다. 평가 원문은 `artifacts/integration-e2e/`, 인수 로그는 `artifacts/integration-handoff/`에 보관합니다.

### 3.3 완료 기준

- 현재 커밋에서 전체 제품 테스트와 평가기 테스트 **전부 통과**. 실행 개수와 로그를 기록합니다.
- `--validate`에서 동결 데이터와 도구 구성 확인이 통과합니다.
- 실제 모델 12문항·16턴을 새 코드로 실행하고, **각 문항의 결과와 실제 함수 인수**를 점검합니다.
- 인수 검증에서 `evidence.source_hashes_match=true`, `data.full_content_verified=true`, 최종 `status=PASS`를 확인합니다.
- 테스트와 평가의 실행일·모델·커밋·로그 위치를 [05 테스트 및 평가](05_테스트_및_평가.md)에 갱신합니다.

**참고:** 현재 인수 스크립트의 전체 테스트 최소 개수는 코드상 `543`입니다. 새 테스트 5개를 필수 회귀 기준으로 확정한다면 검수기의 최소 개수도 최신 기준으로 갱신하고, 그 검수기를 다시 테스트해야 합니다. 단순히 `PASS`라는 단어만 보고 신규 테스트까지 실행됐다고 판단하지 않습니다.

## 4. 2단계 — 모델 입력과 결과 일관성 개선 (P0~P1)

### 4.1 INT-04: 품종 확인 과정에서 이미 입력한 규격 보존

**발견된 문제:** STEP 7 실제 모델 평가에서 사용자가 `특`, `소`, `상자 5kg`를 말했는데도 모델이 등급과 크기를 누락했습니다. 이후 수정에서는 프롬프트·도구 설명을 보완하고 이전에 확정한 조회조건을 관리하도록 했습니다.

**확인할 사용자 시나리오**

1. 사용자가 “품종은 그냥 감귤이고, 특·소·상자 5kg의 7일 가격을 보고 싶다”고 말합니다.
2. 시스템이 세부 품종을 물을 때 **등급·크기·포장·중량·간격**은 이미 입력한 조건으로 보존되는지 확인합니다.
3. 사용자가 “조생귤입니다”라고 답하면 기존 규격으로 조회가 재개되는지 확인합니다.
4. 등급을 실제로 철회하는 별도 요청에서는 철회한 항목만 삭제되는지 확인합니다.

**완료 기준:** 도구 호출 인수와 후속 조건 저장값을 함께 검사하는 회귀 테스트를 통과하고, 실제 모델 응답에서도 입력 누락이 재발하는지 확인한 기록을 남깁니다. 기존 INT-04 자동 채점이 확인하는 범위보다 엄격한 품질 검사가 필요하면 **독립 회귀 문항**으로 추가합니다.

### 4.2 INT-11: 모순된 포장중량 확인·재개

**발견된 문제:** “10kg 박스”와 “포장 한 개 5kg”처럼 같은 물건의 중량이 상충하는 입력에서 사용자가 왜 다시 답해야 하는지 분명하지 않았습니다.

현재 코드의 [`resolve_price_history_request()`](../agents/common/price_history_followup.py)는 모델이 전달한 충돌 목록과 포장 문자열의 중량을 검사해 조회를 보류할 수 있습니다. 확인 전에는 중량값을 조회조건에서 빼고, 사용자가 정정하면 나머지 조건을 활용합니다.

**추가로 점검할 상황**

| 상황 | 기대 동작 |
| --- | --- |
| `10kg 박스`와 `5kg`가 동시에 전달됨 | 두 값이 다름을 설명하고 확인 질문 표시 |
| 사용자가 “5kg이 맞다”고 정정 | 이전 포장명 속 10kg 표기로 다시 충돌하지 않고 조회 재개 |
| 사용자가 중량 대신 7일→14일로 변경 | 미해결 중량 확인 상태는 유지 |
| 모델이 충돌 필드를 누락하거나 표현을 바꿈 | 원문·실제 도구 인수를 검토해 추가 방어 필요성 판단 |

**완료 기준:** 모의 테스트뿐 아니라 실제 모델의 함수 인수·확인 질문·다음 턴 재조회까지 검토합니다. 코드에 없는 예외 사례가 발견될 경우에만 입력 계약을 확장합니다.

### 4.3 화면·PDF·JSON 결과 동기화

직접 조회에서 손익 비교로 전환할 때 화면과 PDF는 새 결과인데 JSON에 직전 결과가 남을 수 있었습니다. `cb87572`에서 `app.py`의 JSON 다운로드 생성 위치를 각 조회·계산 이후로 옮겼습니다.

확인할 흐름은 다음과 같습니다.

```text
가상 손익 계산 → 과거 경락가격 직접 조회 → 손익 계산 → 과거 경락가격 직접 조회
       각 단계에서 화면에 보이는 도구 결과 = PDF 결과 = JSON의 archived_results
```

**완료 기준:** Streamlit `AppTest` 자동 테스트와 사람의 화면 확인에서 전환 직후 결과가 일치해야 합니다. 저장한 비교 JSON을 다시 불러왔을 때 자료 버전·당시 결과와 현재 재계산 결과가 명확히 구분되는지도 점검합니다.

## 5. 3단계 — 데이터 갱신과 저장 파일의 이동성 정비 (P1)

### 5.1 경매 CSV를 갱신하면 왜 과거 가격 조회가 막힐 수 있나요?

현재 시스템에서 일반 시장 참고가격 조회는 **관리자가 선택한 최신 경매가격 스냅샷**을 사용할 수 있습니다. 반면 정현님 과거 가격쌍은 기본 `daily_prices.csv`에서 생성한 별도 파일입니다.

현재 연결 구조는 다음과 같습니다.

```text
관리자 경매 CSV 추가
    ↓
새 경매가격 스냅샷 검증·활성화
    ↓
일반 시장 참고가격: 새 스냅샷을 조회할 수 있음
과거 3·7·14일 가격쌍: 기존 동결 자료 기준으로 남아 있음
    ↓
data_contract.py: 두 원천의 SHA-256이 다르면 VERSION_MISMATCH
    ↓
과거 가격 조회를 보류하고 자료 버전 확인 안내
```

이 동작은 **서로 다른 원천에서 나온 가격과 가격쌍을 섞지 않기 위한 안전장치**입니다. 다만 운영자가 정상적으로 새 데이터를 적용한 뒤에도 과거 가격쌍 조회를 계속 사용하려면 갱신 절차를 개선해야 합니다.

#### 선택지 비교

| 방안 | 동작 | 장단점 |
| --- | --- | --- |
| **A. 동결 비교 데이터 유지** | 갱신된 경매가격과 과거 가격쌍을 별도 버전으로 운영 | 변경량이 작지만 사용자가 두 자료의 기준을 혼동할 수 있고, 활성 가격자료의 새 구간을 과거 가격쌍에서 조회하기 어렵습니다. |
| **B. 새 스냅샷의 가격쌍 함께 재생성** | 새 `daily_prices.csv`로 3·7·14일 가격쌍·품질보고서·해시를 다시 만들고 일괄 활성화 | 운영상 일관성이 높지만 생성·검증·롤백 절차가 추가로 필요합니다. |

**권장 방향은 B**입니다. 같은 버전의 경매가격과 가격쌍을 묶어서 제공하면 사용자가 이해하기 쉽고, 이후 재현도 명확합니다.

#### 구현 순서 제안

1. 신규 경매 원본 CSV를 기존 방식으로 검사하고 스냅샷에 가공 가격표를 생성합니다.
2. **같은 스냅샷의 `daily_prices.csv`**를 입력으로 가격쌍 두 종류와 비교 보고서를 생성합니다.
3. 원천 SHA-256, 컬럼, 건수뿐 아니라 **전체 비교 행 내용**을 독립 재생성 결과와 대조합니다.
4. 모든 검증이 통과하면 가격표·가격쌍·보고서를 **한 버전으로 활성화**합니다.
5. 검증 실패 시 기존 활성 버전을 유지하고, 이전 버전을 다시 선택할 수 있는 복구 경로를 점검합니다.
6. 새 버전이 적용되면 과거 조회조건·화면 결과를 새 자료 기준으로 갱신합니다.

**관련 코드:** [`data_refresh.py`](../agents/juneok/data_refresh.py), [`csv_import.py`](../agents/juneok/csv_import.py), [`build_price_comparisons.py`](../scripts/build_price_comparisons.py), [`data_contract.py`](../agents/common/data_contract.py), [`price_history_service.py`](../agents/common/price_history_service.py).

**완료 기준:** 새 경매가격 CSV를 적용한 후에도 과거 가격쌍 조회와 일반 시장 조회가 **같은 데이터 버전**을 사용합니다. 실패·재시도·롤백 테스트가 포함되어야 합니다. 기존 동결 자료는 이전 평가를 재현할 수 있도록 보존합니다.

### 5.2 같은 자료인데 PC가 다르면 JSON에서 ‘자료 변경’으로 표시됩니다

현재 [`data_revision()`](../agents/juneok/task_context.py)은 자료 명세 해시·활성 선택 파일 해시 외에 **선택된 자료의 절대경로 문자열**도 버전값에 포함합니다.

```text
PC A: C:\SKN projects\jeju-ai-agent-integration\...
PC B: D:\projects\jeju-ai-agent-project\...
```

파일 내용이 같아도 경로가 달라 JSON 복원에서 `data_changed=true`가 될 수 있습니다. 반대로 경로를 무조건 제거하는 것만으로 충분하지도 않습니다. 같은 경로의 파일 내용이 바뀌었을 때는 변경을 식별해야 하기 때문입니다.

#### 개선 방향

- 자료의 **내용 해시와 명세 버전**으로 데이터 동일성을 판정합니다.
- 스냅샷 선택·원천 가격·#855 출하 자료 중 실제 판단에 영향을 주는 파일을 식별합니다.
- 기존 비교 JSON `v1/v2`를 읽을 때 이전 방식의 `data_revision`과 새 방식의 변환·비교 규칙을 정의합니다.
- 예전 JSON의 정보만으로 동일성을 확정하기 어려운 경우, 이를 구분해서 표시하고 현재 자료로 재계산합니다.
- 변경 안내 문구에 ‘데이터 내용이 달라짐’과 ‘버전 정보를 확정할 수 없음’을 구분합니다.

**완료 기준:** 같은 데이터를 다른 폴더·PC로 옮겼을 때는 동일한 자료로 판단하고, 실제 파일 내용이나 활성 데이터셋을 바꾸면 변경이 감지됩니다. 기존 저장 파일의 읽기·검토·복원 회귀 테스트를 유지합니다.

### 5.3 원천 데이터 이용조건과 운영 책임

필수 제주데이터허브 #855의 개별 이용·재배포 조건은 제출·대외 배포 전에 별도 확인이 필요합니다. 경매원천정보와 패키지·글꼴의 이용조건도 최종 배포물 기준으로 기록합니다.

운영 시 정해야 할 사항은 **새 데이터의 확보 담당자, 갱신 주기, 버전 검수·복구 담당자, 보고서에 표시할 출처·관측일**입니다. 확인 결과는 관련 출처 URL과 확인일을 함께 남깁니다.

## 6. 4단계 — 사람 중심 사용성 검증 (P1)

자동 테스트는 코드가 예상대로 움직이는지 보여주지만, 처음 사용하는 사람이 **왜 그 값이 필요한지·무엇을 다음에 눌러야 하는지**는 직접 확인해야 합니다.

### 6.1 추천하는 팀 리허설

참여자에게 사용법을 먼저 설명하기보다, 짧은 과업을 주고 실제로 수행하는 과정을 관찰합니다.

| 과업 | 확인할 점 |
| --- | --- |
| 가상 3,000kg·7일 비교 실행 | 필요한 입력값·기준 단가의 의미를 이해하는지 |
| 감모율을 2%→4%로 변경 | 새 조건이 실제 계산에 반영됐는지, 결과를 읽을 수 있는지 |
| 조생귤 7일 과거 가격 조회 | 출하 손익의 미래 가정가격과 과거 경락가격을 구분하는지 |
| 10kg/5kg 포장중량 충돌 | 안내를 읽고 올바르게 수정할 수 있는지 |
| PDF·JSON 저장·복원 | 화면 결과와 저장한 결과가 일치하는지 |
| 모델 API 키가 없는 PC에서 실행 | 카드·자료 조회를 찾아서 완료할 수 있는지 |

관찰 내용은 **성공 여부, 막힌 지점, 사용자가 이해하지 못한 문구, 도움을 준 시점**으로 기록합니다. 팀원·비전문가 리허설과 실제 농가 현장 검증은 각각 구분해 보고합니다.

### 6.2 현실 출하 조건 점검

현재 손익 비교의 0일은 ‘오늘 즉시 출하가 실현된다’는 보장이 아니라 **현재 판매조건의 기준점**입니다. 실제 사용성 검증에서는 저장시설, 선별·운송, 계약·납품 일정, 출하일 조정 권한, 농가가 확보 가능한 가격·비용 데이터를 확인합니다.

이 항목에서 반복적으로 입력 부담이 발생한다면 필수 입력과 선택 입력을 조정할 근거가 됩니다. 수치 계산의 성공 여부와 실제 행동으로 이어질 수 있는지는 별도로 기록합니다.

팀원별 담당은 기존 구현에 대한 이해도와 실제 작업 가능 시간을 기준으로 협의하면 됩니다. 원래 구현자가 모든 후속 운영을 자동으로 책임지는 방식보다는, **변경할 모듈의 리뷰 담당과 실행 검증 담당을 분리**하는 편이 안전합니다.

### 7.2 병합 준비 순서

1. **통합 기준 확정:** 최신 원격 커밋과 01~06 공식 문서의 기준점을 맞춥니다.
2. **검증 증빙 완성:** 현재 소스에서 전체 테스트·실제 모델 E2E·인수 검증을 통과합니다.
3. **문서 리뉴얼 마무리:** 루트 README 링크 수정, 기존 `docs/휴지통/` 및 개인 문서의 정리 범위를 팀과 합의합니다. 이력이 필요한 자료는 Git에서 조회할 수 있도록 기준 태그·백업을 남깁니다.
4. **남은 문제 처리 결정:** P1 문제를 병합 전에 수정할지, 인수 후 후속 작업으로 남길지 각각 승인합니다. 해결하지 않은 항목은 담당자와 추적 위치를 명시합니다.
5. **Pull Request:** `integration/agents` → `main` PR을 만들고 변경 파일·기능·검증 결과를 팀이 검토합니다.
6. **병합 후 확인:** `main`에서 설치·기본 시연·테스트를 다시 확인하고 결과를 기록합니다.

현재 `main` 대상 정현님 PR **#1**도 열려 있습니다. 정현님 브랜치의 해당 작업이 통합 브랜치에 포함되어 있으므로 중복 반영 여부를 확인한 뒤 PR의 처리 방식을 작성자와 정합니다.
