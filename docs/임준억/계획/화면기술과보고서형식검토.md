# 화면 기술과 보고서 형식 재검토

기준일: 2026-11-09 KST. 사용자 요청에 따라 현재 코드·사용자 여정·프레임워크 공식 문서를 대조한 설계 검토입니다. 아래는 권고안이며 프레임워크 전환·대화/직접 입력 상태 통합·PDF 출력을 구현하거나 실사용으로 비교한 결과가 아닙니다.

## 후속 실행 반영

이 문서는 제안 당시 검토입니다. 이후 사용자의 승인으로 Streamlit 유지·공유 상태·미리보기/PDF를 구현했습니다. 최신 구현/검증은 [공유 상태·PDF 검증](../검증/2026-11-09_공유상태와PDF.md)과 [현재 개발계획](개발계획.md)이 기준입니다. 아래 미구현·후보 표현은 당시 검토의 이력이며 현 구현을 대체하지 않습니다.

## 결론

Streamlit이 모든 단계의 최선이라고 입증된 것은 아닙니다. 현재 선택은 Python 도구와 로컬 실행·검증을 빠르게 연결하는 데 적합했습니다. 사용자 여정에 더 적합한 방향은 대화를 중심으로 필요한 조건을 구조화해서 확인·수정하는 화면입니다. 이 경험은 Streamlit 안에서도 상당 부분 구현할 수 있으므로 현재 MVP에서는 그 가능성을 먼저 확인하는 것이 합리적입니다.

이는 마감 때문에 친숙한 UI를 포기하자는 판단이 아닙니다. 기술 전환보다 대화 시작의 부담, 조건 확인·정정, 동일 상태 유지, 결과 이해·공유가 실제로 개선되는지로 선택합니다. 장기 제품에서 화면·대화·문서 패널을 세밀하게 제어해야 한다면 React 기반 전용 UI를 강한 후보로 둡니다. 기존 Python 도구·검증·하네스는 재사용하는 방향입니다.

## 현재 설계의 원인과 문제

app.py는 이미 st.chat_input/st.chat_message를 사용합니다. 현재 네 탭과 대화/직접 입력의 별도 조건은 Streamlit의 강제가 아니라 프로젝트에서 선택한 설계입니다. 별도 도구 경로는 키 없는 실행 검증에 유용하지만, 일반 사용자가 대화와 폼을 오가며 동일 조건으로 비교하기에는 재입력·혼동을 유발할 수 있습니다.

화면의 사용자 경험과 구현 프레임워크를 구별합니다. ChatGPT·Claude와 같은 입력창·메시지·결과 패널 구성을 참고하는 것은 해당 서비스에 프로젝트를 연결하거나 모델/하네스를 바꾼다는 뜻이 아닙니다. 전체 비전문가가 이 제품들에 익숙하다고 확인한 것은 아닙니다. 빈 대화창만으로 시작할 수 있다는 가정도 검증되지 않았습니다.

## 기술 후보 비교

아래 비교는 현재 코드와 문서에서 도출한 정성 판단이며 시간·성능의 실측 순위가 아닙니다.

| 후보 | 여정에 제공할 수 있는 점 | 우리 프로젝트에서 추가 확인할 점 | 현재 권고 |
| --- | --- | --- | --- |
| Streamlit 유지·대화 중심 재구성 | 대화 안에 표·입력 요소 배치, Python 상태·도구·로컬 CSV 직접 재사용 | 대화 내 수정·고정 조건 요약·작은 화면·스크롤/포커스 경험. 재실행 시 상태 보존 | MVP의 우선 후보. 현재 탭 구조 유지가 아니라 경험 재설계 |
| React 전용 UI + Python backend | 대화·조건 카드·결과/문서 패널·반응형 동작의 세밀한 제어 | API/세션/오류/중복 요청/다운로드 연결, 빌드와 로컬 설치 재검증 | 장기 제품과 전용 UI 요구가 커질 때 강한 후보. 현재 자동 전환은 미확정 |
| Chainlit | 대화·메시지 요소·동작 버튼 중심의 Python UI | 공식 문서가 현재 저장소 보관·유지보수 중단을 명시 | 현재 새 기반으로 채택하지 않음 |

React가 센터에서 반드시 Node 서버를 요구하는 것은 아닙니다. 빌드한 정적 파일과 Python API를 함께 배포하는 구성도 가능하며, 실제 설치·운영 비용은 구성을 정해 검증해야 합니다. 어떤 후보도 현재 공개 사양에서 설치·성능 비교를 수행하지 않았습니다.

공식 근거: [Streamlit 대화 요소](https://docs.streamlit.io/develop/api-reference/chat)는 대화 컨테이너 안의 표·차트·다른 요소 배치를 설명합니다. [assistant-ui 구조](https://www.assistant-ui.com/docs/architecture)는 UI/runtime/backend 계층과 자체 API 연결을 구분합니다. [Chainlit 프로젝트 상태](https://docs.chainlit.io/get-started/project-status)는 유지보수·보안 업데이트·지원 중단을 안내합니다. 기능 가능성과 우리 구현의 검증 완료를 구분합니다.

## 여정에 따른 화면 권고

| 여정 | 다음 설계에서 확인할 개선 |
| --- | --- |
| 진입 | 시작 카드: 출하 조건 비교 / 과거 출하자료 조회 / 용어 이해. 첫 화면에 파일·개발 설정을 요구하지 않음 |
| 조건 제공 | 한 번에 긴 폼을 내기보다 부족한 항목만 질문. 모름/0·해당 기간 전체 감모·가격 기준을 짧은 설명과 선택으로 확인 |
| 조건 확인 | 대화 옆 또는 펼침 영역에 현재 조건·미확인·가정 표시. 사용자가 사실이라고 표시한 값도 외부 사실 검증으로 표현하지 않음 |
| 수정 | 조건 카드 수정과 대화 변경이 동일한 Python 상태·버전 계약을 사용. 다른 값 보존·기간 변경 시 감모 재확인 |
| 결과 이해 | 핵심 조건과 필요한 최소 단가를 먼저 제시하고 산식·출처·자료 한계·진단 로그는 필요할 때 열기 |
| 공유·재방문 | 현재 결과의 버전·가정·자료 출처를 고정한 보고서 미리보기와 저장. 과거 대화 결과와 현재 결과 구분 |
| 자료 관리 | CSV 추가·키/연결 상태·진단은 별도 관리 영역. 키 없는 직접 도구 경로는 유지하되 일반 사용자에게 두 입력 상태를 강요하지 않음 |

동일 상태 통합은 아직 제안입니다. 구현 시 직접 입력을 화면 상태 복사로만 통합하지 않고 기존 ScenarioStore의 버전·원자 갱신·철회·감모 재확인 계약을 통과시켜야 합니다. UI 변경 때문에 API 키가 브라우저에 전달되거나 수치 계산이 모델/브라우저로 옮겨가지 않게 합니다.

## 보고서가 MD인 현재 이유와 한계

현재 app.py는 render_report의 문자열을 text/markdown, .md 파일로 내보냅니다. CLI·화면·보고서가 같은 Python 결과와 렌더러를 사용하므로 내용 대조·버전 기록이 쉽고, 별도의 문서 변환 의존성 없이 실행됩니다. 초기 구현·검증 편의에 맞춘 선택입니다. 비전문가의 최종 보고서 형식으로 가장 적합하다는 사용자 검증을 거친 선택은 아닙니다.

Markdown은 Agent 또는 Streamlit의 필수 형식이 아닙니다. [Streamlit 다운로드 API](https://docs.streamlit.io/develop/api-reference/widgets/st.download_button)는 문자열·바이트와 MIME 형식을 받아 다른 파일 형식도 전달할 수 있습니다. 단, 버튼이 PDF를 자동 생성하는 것은 아니며 별도 생성기를 구현해야 합니다.

일반 사용자가 MD를 열었을 때 표 구문이 그대로 보이거나 추가 앱이 필요한 것은 열람·인쇄·공유 단계의 마찰이 될 수 있습니다. 프레임워크 선택과 보고서 형식은 별도 결정입니다.

## 출력 형식 권고

- 앱 안의 보고서 미리보기: 바로 읽고 내용·조건을 확인하는 기본 경로.
- PDF: 일반 사용자용 기본 저장·인쇄·공유 후보. 한글 글꼴·긴 표/줄바꿈·여러 대안·출처·가정·조건 버전·다운로드 오류를 검증한 뒤 기본 형식으로 승격.
- CSV: 사용자가 계산 표를 엑셀 등에서 재활용할 때 선택 제공. 조건·단위·출처가 빠지지 않도록 보고서와 연결.
- MD: 개발·검증·텍스트 재사용을 위한 보조 형식으로 유지.

출력은 LLM으로 다시 작성하거나 새 계산을 수행하지 않고 같은 결과 객체에서 만들며, PDF/화면/CSV의 숫자·단위·입력 구분·버전·출처를 대조합니다. HTML 미리보기와 브라우저 인쇄는 중간 구현 후보지만, 사용자가 직접 인쇄 설정에서 PDF를 저장해야 하는 방식은 한 번의 PDF 다운로드와 같은 경험으로 간주하지 않습니다. 다운로드 형식 추가 자체를 프레임워크 전환 사유로 보지 않습니다.

## 다음 판단 기준과 한계

먼저 작은 대화 중심 흐름에서 U01 비교→U02 감모 정정→U03 가정 범위→보고서 열람을 확인합니다. 조건 재입력·기존 값 손실·같은 내용 반복 질문·과거 결과 혼동·파일 열람 문제를 관찰 기준으로 둡니다. 현재 자동/브라우저 검사115개를 새로운 화면의 사용자 이해도 증거로 사용하지 않습니다.

Streamlit에서 이 핵심 흐름이 불안정하거나 전용 패널·작은 화면·조작 제어 요구를 무리한 우회로만 충족한다면 React UI를 같은 도구/상태 조건으로 비교합니다. 단순 외관 취향이나 지금까지 작성한 코드량만으로 결론 내리지 않습니다. 농가·비전문가의 선호/친숙함은 아직 미검증입니다.
