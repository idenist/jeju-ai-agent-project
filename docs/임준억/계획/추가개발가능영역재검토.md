# 추가 개발 가능 영역과 우선순위 재검토

후속: 사용자가1·2번과 통과 후3번을 승인해 구현했습니다. 이 문서는 당시 권고 기록으로 보존하며 현재 판정은 [구현 검증](../검증/2026-11-09_자료탐색과역산및변경검토.md)과 개발계획을 확인합니다.

2026-11-09 KST / 현재 개인 후보 기준. 사용자는 개발을 마무리하기 전에 남은 개발 가능 영역을 검토하도록 요청했습니다. 이 문서는 후속 **권고안**이며 새 기능 구현·팀 채택을 승인받았다는 뜻은 아닙니다.

## 판단

개발 가능한 유의미한 영역이 남아 있습니다. 직전 계획은 안정성·인수·제출 준비에 무게가 실려 제품 과업 확장을 충분히 다루지 못했습니다. 리허설·이용조건 검수와 별개로 추가 개발을 진행할 수 있습니다. 권고는 **자료 탐색/선택 → 제안조건의 허용 한계 계산 → 저장 비교와 변경 검토** 순서입니다. 실제 출하·정산 기록은 그 다음 업무 확장 후보입니다.

현재 기능은 조건이 정해진 뒤의 비교에 강합니다. 사용자가 어떤 자료를 골라야 하는지, 받은 제안가격에서 어떤 비용/감모까지 가능한지, 지난 검토와 무엇이 달라졌는지까지 이어주면 같은 주제 안에서 실용성이 커질 가능성이 있습니다. 이 판단은 코드·확보 CSV·공식 목적을 대조한 설계 의견이며 농가 효과 검증은 아닙니다.

공식 대회는 비전문가가 데이터 탐색부터 분석 결과까지 이용할 수 있는 Agent를 요구합니다. 따라서 자료를 찾고 조건을 좁히는 자동화도 핵심 개발입니다. [공식 안내](https://daker.ai/public/hackathons/jeju-ai-bigdata-agent-challenge). 제주농업기술센터의 2018년 자료에는 저장 중 품질·감량 변화와 선별 출하 업무가 연결되어 있습니다. 이는 인접 업무 방향의 참고이며 현재 농가의 감모율·보관조건·효과를 정하는 근거로 쓰지 않습니다. [당시 영농정보](https://agri.jeju.go.kr/files/board/5c2629c1-ee1e-47ad-9615-cd7b9040ffe8.pdf).

## 현재 구현에서 확인한 빈틈

| 확인한 코드/자료 | 현재 동작 | 남은 과업 |
| --- | --- | --- |
| evidence.py의 get_market_evidence·tools.py | 정확한 시장/품종/등급/크기/포장/중량을 받아 최근 관측 한 건을 조회 | 데이터에서 실제 가능한 선택을 찾아주는 도구가 없음. 조회 목록을 모르는 비전문가에게 입력 부담 |

| comparison.py·insights.py | 필요한 미래 최소단가와 지정 가정 조합의 금액 차이를 계산 | 주어진 제안단가에서 허용 감모·보관비를 역산하는 기능 없음 |
| casefiles.py·app.py 복원 | JSON 저장·확인·명시적 복원 후 재계산. 과거 결과는 보관 | 현재 상태를 바꾸지 않고 과거 비교와 나란히 변경 검토하는 화면/도구 없음 |
| state.py·workspace.py | 조건 변경 이력·이번 비교 맥락 보존 | 실제 출하·정산의 별도 기록과 예정 조건 대조는 미구현 |

선택된 경매 스냅샷을 읽어 **1,743행, 시장1개·품종8개·등급9개·크기27개·실제 결합 규격167개**를 확인했습니다. 관측범위는2026-10-01~11-06입니다. 분류별 목록을 독립 조합하면 실제 없는 거래조건을 만들 수 있으므로 결합 조건으로 좁혀야 합니다. `artifacts/development-review/feasibility.json`에 읽기 전용 점검 결과를 보존했습니다. 별도 수집 API나 새 데이터가 필요한 첫 기능은 아닙니다.

## 권고 1 · 확보 자료 탐색과 조건 선택

사용자 과업: “어떤 감귤 자료가 있나?”, “가락시장 조생귤 중 내가 고를 수 있는 규격을 찾아줘.”

- CSV에서 실제 가능한 시장명/코드·품종·등급·크기·포장/중량의 결합을 찾는 읽기 전용 도구를 둡니다. #855도 실제 품종·연도/월·부분월 여부를 탐색합니다.
- Agent는 이미 선택한 값으로 후보를 좁히고 남은 선택만 묻습니다. UI도 같은 후보를 사용합니다. 목록이 길면 개수 제한/이어보기를 설계해 맥락 예산을 지킵니다.
- 코드에 있던 예시 품종을 모든 데이터의 정답으로 간주하지 않고, 빈 후보·동명이코드·희소 관측·자료 버전 변경을 드러냅니다.
- 출하 품종과 경매 품종은 별도 분류로 유지하고 사용자 확인 없이 자동 매핑하거나 시장값을 제시가격에 대입하지 않습니다.

완료기준: 존재하지 않는 결합을 제안하지 않음, 선택 변경 시 종속 선택 무효화, 실제 관측기간/자료 버전 표시, 키 없는 UI와 자연어 도구가 같은 선택 결과를 사용, NO_DATA/모호성/자료 교체 검사. 현재 단가로 직접 비교하는 경로는 자료 탐색 없이 계속 동작해야 합니다.

가치: 대회 취지와 직접 연결되고 비전문가 입력 부담을 줄일 수 있습니다. 코드 영향은 중간이며 공통 수집/전처리·새 DB·팀원 도구 병합을 요구하지 않습니다.

## 권고 2 · 제안단가에서 감당 가능한 조건 역산

사용자 과업: “7일 뒤3300원/kg에 판다고 가정하면 감모가 몇%까지 가능한가?”, “감모2%라면 하루 보관비를 얼마까지 감당할 수 있나?”

- 기존 Decimal·가격 기준·중복 비용 검사를 재사용해 손익분기 허용 감모율 또는 보관비 상한을 계산합니다. 한 번에 풀 변수 하나와 고정할 조건을 명시합니다.
- 실제 제안과 사용자 가정을 구분하고 값/기간/실행 제약이 빠졌으면 확인합니다. 감모율과 보관비의 각각 상한을 동시에 충족 가능한 조합으로 오해하지 않게 설명합니다.
- 입력한 가정 목록의 결과가 모두 같은 쪽인지/뒤집히는지 요약하고, 사용자가 실제로 확인할 항목을 연결할 수 있습니다. 표 밖 확률·임의 가정 범위를 만들지 않습니다.

가상 검산: 현재3000kg×3000원, 7일·일 보관비20000원, 미래3300원 가정이면 감모 상한은 약7.6767%입니다. 기존 계산기에7.67%를 넣으면 차이+670원,7.68%면-320원으로 경계를 확인했습니다. 감모2%를 고정하면 일 보관비 상한은 약100285.71원입니다. 이는 설계 타당성 검산이며 새 역산 도구가 구현·검증됐다는 뜻은 아닙니다.

완료기준: 경계 전/후 독립 정답, 원 단위/감모율 반올림의 보수적 처리,0가격·음수 비교금액·가능한 비음수 해 없음·수수료/항목별 비용·복수 대안 검사, 기존 상태 불변, 대화/카드/PDF 수치 일치. 기간이 늘면 감모도 달라지므로 최장 보관일을 단일 감모로 자동 산출하는 기능은 포함하지 않습니다.

가치: 가격 한 개를 알려주는 수준에서 실제 가격/비용 확인에 쓸 수 있는 기준으로 넓힙니다. 코드 영향은 중간이며 새 외부 데이터·예측 모델이 필요하지 않습니다. 실제 협상·출하에 유용한지는 사람 검증이 남습니다.

## 권고 3 · 지난 비교와 변경 사항 검토

사용자 과업: “지난번 저장한 검토와 비교해서 어떤 조건이 달라졌고 계산이 얼마나 바뀌었나?”

- 기존 v1/v2 JSON을 읽기 전용으로 확인하고 현재 조건과 나란히 비교합니다. 파일 확인만으로 현재 상태를 덮어쓰지 않습니다.
- 물량·가격 기준·비용·기간·감모·실행 가능성·조회조건·자료 버전 변경과 결과 차이를 표시합니다. 대안 추가/삭제·대응 불가도 명시합니다.
- 당시 저장 결과와 현재 코드/조건으로 재계산한 결과를 구분합니다. 서로 다른 품종/거래규격이나 다수 변경의 차이를 단일 원인의 효과로 단정하지 않습니다.
- 기존 복원 버튼은 별도 명시 동작으로 유지하고 비교 건의 연속성을 지원합니다. 사용자 계정·장기 프로필 없이 가능합니다.

완료기준: 읽기/비교의 상태 불변, v1/v2·오류 파일·대안 추가삭제·기준 차이·자료 변경·누락 입력, 과거와 현재 표시 및 PDF 재현. 코드 영향은 중간입니다. 이미 있는 저장/복원 기능과 구별되는 새 과업입니다.

| 프레임워크 교체·다중 Agent·벡터 DB | 지금 우선순위 낮음 | 현재 확인한 제품 빈틈과 직접 연결되는 필요성이 부족함 |

큰 기능을 뒤로 둔 이유는 가용시간뿐이 아닙니다. 계산 단위·데이터 확보·현장 근거·팀 주제 변화의 영향이 더 큽니다. 실제 구현 속도와 검증 결과에 따라3번/정산 기록까지 진행 여부를 판단합니다. 무조건 좁은 MVP에서 멈추는 결론은 아닙니다.

## 실행 순서 제안과 유지 기준

1. 현재188개·CSV/명세·공유 상태를 기준선으로 고정합니다. 원격 반영 단위 정리는 별도 과업입니다.
2. 1번을 구현하고 존재/모호성/자료 변경·키 없는 사용·자연어 선택을 검증합니다.
3. 2번을 구현하고 독립 경계 정답·누락/철회·기간 변화·상태 불변·UI/PDF를 검증합니다.
4. 앞 두 기능이 유지 기준을 충족하면3번을 붙입니다. 기능별 관련 검사→전체 회귀→한국어 과업 반복→분리 인수본을 확인합니다. 횟수만 늘리지 않고 바뀐 경로의 실모델 평가를 수행합니다.
5. 각 단계 결과를 보고 정산 기록의 최소판을 추가할지 재판단합니다. 리허설과 이용조건 확인은 개발과 병행합니다.

팀 합의가 필요한 것은 대표 기반·공통 데이터/상태 계약 변경·팀원 도구 연결·부분 출하/정산까지의 공식 범위·역할·최종 UI입니다. 개인 후보 안에서 읽기 전용 탐색·계산·변경 검토를 구현하는 결정과 팀 공통 채택을 구분합니다. 이번 검토로 제품 코드·API 호출·팀 통합·commit/push를 수행하지 않았습니다.
