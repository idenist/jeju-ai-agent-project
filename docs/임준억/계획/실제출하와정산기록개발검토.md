# 실제 출하·정산 기록의 실용성과 개발 범위 검토

2026-11-09 KST / 기준: 원격 dev/juneok의 기능66af959·인수/README9149d54. **A 출하 기록+B 정산 검산을 로컬 구현했습니다.** 기존226개+신규31개 총257개 유지 확인. [구현·검증 결과](../검증/2026-11-09_실제출하와정산검산.md)를 현재 판정으로 읽고 아래 설계 이유/가상 예시를 보존합니다. C 당시 가정 대조·D 실제 양식 검증은 후속입니다.

## 판단과 해결할 일

개발할 가치가 있습니다. 권고 범위는 **한 출하 검토 건에 실제 실행 결과를 연결하고, 정산내역을 검산한 뒤 당시 가정과 달라진 점을 확인하는 기능**입니다. 사용자가 제안했던 생애주기 중 출하·정산을 연결하는 인접 확장입니다. 거래내역 입력 자체만 추가하면 기존 엑셀/출하 시스템과 중복되고 재입력 부담이 커질 수 있습니다. 누락·중복 비용 확인과 이전 검토의 재사용을 함께 제공해야 실용성을 검증할 수 있습니다.

예상 사용자 과업은 “실제 정산서를 받았는데 얼마가 공제됐고 추가로 낸 비용까지 보면 어떤가?”, “지난 검토에서 가정했던 물량·기간·가격과 무엇이 달랐나?”, “다음 비교에 참고할 기록은 무엇인가?”입니다. 농가 인터뷰·정산서 표본으로 확인한 수요는 아니므로 사용성/효과의 가설로 둡니다.

## 확인한 근거와 현재 자료의 한계

- aT KAMIS의 [2024년 유통실태 종합](https://www.kamis.or.kr/customer/circulation/domestic/analysis.do?action=detail&brdctsno=464693&pagenum=1&search_keyword=&search_option=)은 감귤을 포함한 유통비용·거래실태의 표본 조사입니다. 개별 농가의 실제 비용이나 우리 서비스의 효과 자료로 사용할 수 없습니다. 비용 구분이 필요하다는 업무 배경으로만 참고합니다.
- 서울시농수산식품공사의 [전자송품장 통합홈페이지](https://einvoice.garak.co.kr/)에는 출하물량·운송물량·정산자료와 로그인 메뉴가 있습니다. 기존 업무 시스템과의 중복 가능성을 확인했습니다. 실제 계정 자료·제공 필드·외부 연동 API·허용 범위는 확인하지 않았습니다.
- 현재 auction_trades.csv의36개 컬럼에는 거래일·규격·물량·가격·거래 정산일자 등이 있지만 농가 개인의 수수료/공제 내역·별도 비용·은행 입금 확인 필드는 없습니다. daily_prices.csv는 규격별 집계입니다. 이 자료로 사용자의 개인 정산을 자동 완성할 수 없습니다. 송품장 관련 번호나 거래 정산일자를 개인 정산서/현금 수령 증거로 간주하지 않습니다.
- ScenarioStore는 출하 전 비교 조건이고 casefiles는 그 조건·가정·조회 선택의 저장/복원입니다. 현재 날짜·실제 판매·정산·입금의 기록 모델은 없습니다. 실제 결과를 기존 가정 필드에 덮어쓰면 비교 기준을 잃습니다.

현재도 농가 참여자와 익명화한 실제 정산서는 없습니다. 가상 자료로 기능을 검증하고, 실제 양식/업무 적합성은 별도 미검증으로 유지해야 합니다.

## 금액·물량 계약의 핵심

1. **정산서 공제와 정산 밖 비용을 분리합니다.** 매출G, 정산서 공제D, 정산서 지급액N, 외부 비용E를 두고 G-D와N의 차이를 검사합니다. N-E는 입력한 비용 반영금액입니다. 농가 전체 순이익으로 표시하지 않습니다. N을 입력했는데 D를 다시 차감하지 않습니다.
2. **정산과 입금은 별개입니다.** 정산서 지급액을 실제 입금액으로 자동 저장하지 않습니다. 선택 입력한 입금액과 정산서 금액을 대조할 수 있지만 은행 계좌·거래내역 연동은 하지 않습니다. 미입금/부분입금 여부는 제공된 정보 이상으로 판단하지 않습니다.
3. **미확인과0을 구분합니다.** 별도 비용을 모르면0으로 마감하지 않습니다. 확인된 범위의 검산과 남은 항목을 표시합니다. 추정 비용/과거 가정을 실제 비용으로 자동 전환하지 않습니다.
4. **수량 차이와 감모는 별개입니다.** 처음 물량-판매중량을 모두 감모로 간주하지 않습니다. 미판매 잔량·폐기·중량 기준·계측 차이가 확인돼야 감모를 구분할 수 있습니다. 상자 중량과 실중량도 분리합니다.
5. **원래 가정의 기준을 보존합니다.** 가격의 gross/commission_net, 이미 포함한 비용, 제외했던 비용이 정렬되지 않으면 금액 차이를 차단하거나 확인 질문을 합니다. 미래가격을 입력하지 않았던 비교에는 예상 수익 오차를 만들지 않습니다.
6. **검토 차이를 효과로 주장하지 않습니다.** 실제 기록과 당시 제시가격/가정의 차이는 조건부 대조입니다. 실행하지 않은 즉시 출하의 실제 결과는 관측하지 않았으므로 “보관 덕분에 번 금액”을 산출하지 않습니다.

같은 비용 범주가 정산서와 외부 비용에 나타나면 실제로 동일 비용인지 확인합니다. 운송비라는 이름만 같다고 서로 다른 운송을 자동 삭제하거나, 동일 항목을 두 번 차감하지 않습니다.

## 가상 검산 예시

실제라고 입력한 판매중량2940kg·단가3300원/kg라는 **가상 정산 기록**을 가정합니다. 매출9702000원, 판매수수료485100원, 정산서 운송비60000원이면 지급액은9156900원입니다. 정산 밖 보관비140000원을 별도로 냈다면 입력 비용 반영금액은9016900원입니다.

입금액9156900원을 받았다는 입력은 정산서 지급액과 일치하지만 전체 순이익9016900원을 증명하지 않습니다. 원래 비교가 동일 비용 제외 방식이었다면 운송비 등 기준을 확인하기 전에는 원래 비교금액과 실제 결과의 차이를 자동 산출하지 않습니다. 실제 농가 자료·실행 도구가 아니라 Decimal 식의 설계 검산이며 artifacts/settlement-review/feasibility.json에 보존했습니다.

## 데이터·구조 제안

새 ShipmentRecord를 기존 ScenarioStore와 분리합니다. 원래 비교ID/스냅샷·자료 버전·해시와 선택 대안을 참조하고, 실행 결과/정산 초안/사용자 확인/정정 버전을 따로 둡니다. 기록을 수정해도 출하 전 가정과 당시 계산은 바뀌지 않습니다.

파일은 기존 비교 JSON v1/v2를 그대로 두고 별도 `jeju-shipment-record` v1 같은 형식으로 제안합니다. 실제 필드/형식은 구현 전 확정합니다. 입력량/단위/날짜/금액·중복 필드·비정상 숫자·용량·해시·원자 가져오기 검사는 기존 방식을 재사용합니다. 내보내기/가져오기와 삭제 범위를 사용자에게 명확히 보여줍니다.

개인식별·계좌·연락처는 이 과업의 필수 필드로 만들지 않습니다. 키 없는 카드와 로컬 파일 흐름을 우선하고 서버에 자동 영구 저장하지 않습니다. 대화 추출을 사용하면 전송되는 정보와 확정 전에 확인할 초안을 구분하며, 신원/계좌가 있는 정산서 원문을 기본 경로로 모델에 보내지 않습니다.

제안 도구는 입력 초안/확인, `reconcile_settlement`, `compare_realization_to_case`처럼 역할을 나눕니다. 이는 아직 등록한 함수명이 아닙니다. 모델은 입력 해석·누락 질문·설명을, Python은 상태 변경 확인·정확한 합산·기준 일치 검사·보고서를 담당합니다. 자동 프로필/감모 학습은 넣지 않으며 다음 비교에 값을 쓰려면 사용자가 기간/조건을 다시 확인합니다.

## Citation 추가 완료 기준

[출처와 계산 근거 인용 점검](../검증/2026-11-09_출처와계산근거인용점검.md)을 적용합니다. A에서 필드별 입력 경로·확인 상태·수정 버전과 불변 비교 참조를 저장하고, B에서 계산식/규칙 버전·고정 입력 참조·비용 범위를 핵심 금액에 연결합니다. UI·PDF·JSON은 같은 근거 ID를 사용합니다. 대화는 자료·수치·판단 답변에 근거 참조를 제공하고, 단순 누락 질문/수정 확인에는 외부 인용을 강제하지 않습니다. 핵심 문장 옆 짧은 참조와 펼쳐 보는 상세를 사용하며 매 답변 웹 검색을 요구하지 않습니다. 실제 파일이 없으면 정산서 페이지/외부 검증 근거를 만들지 않습니다. 공개 자료는 URL·관측일·조회 조건·내용 해시·집계 방식을 연결하며, 해시를 진위 보증으로 표시하지 않습니다. 끊긴 참조·오래된 계산·미확인 값의 실제 값 승격을 실패로 검사합니다. 기존 도구의 공통 근거 구조 정렬은 후속 보강으로 구분합니다.

[공식 자료·팀 방향 정합성 점검](../검증/2026-11-09_공식자료와팀방향인용정합성.md)을 적용합니다. #855 실제 분석을 기존 핵심 여정에 유지하고 A+B는 출하 검토에 연결되는 개인 확장으로 둡니다. 모든 답변 citation은 공식 필수 조항이 아니라 근거 확인을 돕는 설계 선택입니다. 정산 공개 시연/제출 샘플은 가상 자료를 사용합니다. 근거 라벨/URL/공유 PDF에 개인 파일명·경로·식별자·계좌 정보를 기본 노출하지 않습니다. 개인 금융 기록의 명시적 로컬 내보내기는 공유용 제출물과 분리하며 실제 기록은 패키지에서 제외합니다. 실제 금융정보가 섞인 공개 출력/패키지를 실패로 검사합니다. 매 응답 웹 검색을 도입하지 않고 기존 CSV 경로를 유지합니다. 최소 하드웨어 사양을 실제 센터 권한·OS·계정 확보로 해석하지 않습니다. 대표 구조·공통 근거 스키마·정산 기능의 팀 채택은 별도 합의입니다.

A+B 구현 및 검증을 완료했고, C는 후속 설계/개발 범위입니다. 자연어 입력 초안→확정은 C와 함께 검토하며 현재 Agent는 카드 확인 기록을 로컬에서 읽기 전용 검산하고 모델 이력에는 금액 없는 처리 상태만 전달합니다. 기존226개 유지→신규 정상/오류/독립 정답→UI/PDF→도구명을 알려주지 않는 한국어 반복→키 없는 분리 인수본 순서로 확인합니다. 사람 검증은 프로그램 통과 수로 대신하지 않습니다.

## 실용성을 다시 판단할 기준

- 사용자가 기존 정산 자료에서 필요한 항목을 옮길 수 있는가? 정산 시스템을 이미 쓰는 경우 추가 입력 부담보다 검산/이전 검토 대조가 도움이 되는가?
- 누락·중복·다른 비용 기준을 실제로 찾는가? 단순 설명보다 다음에 확인할 내용을 구체적으로 제공하는가?
- 이전 비교를 연결하는 데 걸린 시간·수정/도움 횟수·정산/입금/이익 구분 이해를 관찰할 수 있는가?

농가 접촉·실제 양식 없이 “사용할 만하다”나 수익 효과를 확정하지 않습니다. 가용시간 외에도 실제 정산서의 다양성·재입력 부담·금액/비용 정의가 주요 제약입니다. 공개 가격 API 추가만으로 이 공백이 해소되지 않습니다.

## 팀 합의와 개인 진행 구분

개인 후보의 분리된 기록/검산 도구·키 없는 UI·가상 자료 검증은 다음 개발로 제안할 수 있습니다. 실제 구현은 사용자 검토 후 시작합니다. 대표 제품에 실제 거래 기록을 포함할지, 팀 공통 ID/저장 형식·정산 필드·보존/삭제·기관 연동·역할을 채택할지는 중간발표 이후 팀 합의입니다. main·팀원 도구를 지금 수정하거나 통합하지 않습니다.

기관 계정/정산 API 연동·OCR·여러 농가 DB·부분 출하·전체 재배 생애주기·수익 예측은 이번 첫 범위에 넣지 않습니다. 해당 방향은 폐기하지 않고 실제 데이터·운영 조건·수요 확인 후 재검토합니다.
