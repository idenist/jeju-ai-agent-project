# 센터·챌린지·팀 기준의 하네스 재검토

검토일 2026-11-09 KST / 개인 후보 범위 재검토. 사용자 장기 메모리는 사용자 아이디어이며 팀 채택 기능이 아닙니다. 이전 [외부 레퍼런스 검토](하네스외부레퍼런스검토.md)와 [컨텍스트·장기 메모리 검토](컨텍스트와사용자장기메모리검토.md)의 권고를 실제 배포 목적에 맞춰 다시 평가했습니다. 이번에는 코드 변경·새 기능 구현을 하지 않았습니다.

## 판단

**이번 검토 과업의 연속성·실패 복구·재현성은 우선 보강하고, 사용자 계정 기반 상시 장기 메모리는 후속 선택안으로 둡니다.** 기억 자체를 포기하는 것이 아니라, 이번 비교를 이어가는 기억과 사람에 대한 누적 프로필을 구분합니다. 범위 조정의 주된 이유는 시간 부족이 아니라 목적 적합성·운영 조건·통합 비용입니다.

## 이번 과업 맥락의 구체적 의미

현재 ScenarioStore는 주로 계산 수치를 담습니다. 따라서 긴 대화 관리를 할 때 숫자 상태만 남기고 나머지를 잘라내면, 사용자가 무엇을 검토하려 했는지와 어느 품종/기간을 명시했는지 놓칠 수 있습니다. 이를 작게 구조화하는 방안을 권고합니다.

예시: 검토 목적, 현재 비교 건 ID, 명시한 출하통계 품종/월/기간, 선택 시장 규격, 사용자가 정한 가정 범위, 미확인 질문, 확인/변경 이유, 상태·자료 버전. 이는 구현 제안이며 현재 저장 필드로 이미 존재한다는 뜻은 아닙니다.

모델 입력은 시스템 계약 + 최신 ScenarioStore + 관련 과업 맥락 + 최근 완전한 대화/필요 도구 결과로 구성합니다. 수치의 기준은 계속 Python 상태이며 자연어 요약이 덮어쓰지 않습니다. 맥락 정리 시 function_call과 output을 분리하거나 원래 가정·철회·새 기간 확인을 없애지 않습니다.

JSON 복원을 활용하면 장기 연속성의 일부를 제공할 수 있습니다. 저장할 검토 이유·미확인 항목을 추가한다면 기존 v1 호환·가져온 텍스트의 비신뢰 데이터 취급·명시적 복원·자료 변경 후 재계산을 함께 검증합니다. 이를 ‘사용자를 자동으로 기억하는 프로필’이라고 부르지는 않습니다.

## 팀 입장에서의 채택 가능성

팀이 채택할 후보로는 데이터·계산 도구와 독립적인 입출력 계약, 한 실행의 종료 원인·상태·자료 버전, 작은 과업 맥락 계층, 재현 가능한 검사가 유리합니다. 다른 팀원에게 사용자 계정·특정 DB·프로필 구조를 먼저 도입하도록 요구하는 구성은 통합 비용을 늘립니다. 이는 현재 코드와 합의 기록에 따른 해석이며 팀원의 실제 평가 발언을 대신하지 않습니다.

개인 실험과 팀 공통 채택은 별개입니다. 개인 프로필 기능을 별도로 실험하는 것은 가능하지만 기본 실행·CSV·모델 도구·계산을 해당 기능에 종속시키지 않는 방향을 권고합니다. 지금 대표 하네스나 팀원 도구를 병합하지 않습니다.

## 실행 순서 권고와 완료기준

1. 유지할 계산/자료/상태 계약과 과업 맥락·초기화/복원 범위를 정합니다.
2. 실패 원인·반복 감지·부분 결과 복구를 보강하고, 과업 맥락을 보존하는 최소 입력 예산을 적용합니다.
3. 함수명을 알려주지 않는 한국어 과업을 여러 번 평가합니다. 긴 대화 전/후·철회·기간 변경·미관측·조회조건·복원 뒤 결과를 확인합니다.
4. 기존 162개 유지와 신규 정상/실패 검사를 확인해 개인 후보를 원격에 반영하고 README·매뉴얼·시연·기획서 근거를 맞춥니다.
5. 중간발표에서 대표 구조·도구 연결과 함께 지속 프로필의 사용자 수요·센터 운영 조건을 논의합니다. 최종 기능/역할 선택은 팀이 결정합니다.

컨텍스트 정리를 ‘무조건 대화 요약 모델 추가’로 구현하지 않습니다. 실제 요청 크기·호출/토큰·지연·상태 보존을 측정하고 필요한 최소 방법을 고릅니다. 기존 30턴 문자 수 증가는 예산 설계의 신호이며 실제 서비스 실패나 성능 저하 측정은 아닙니다.

이번 권고는 이전 장기 메모리 우선 구현 권고를 목적에 맞게 조정합니다. 장기 메모리 아이디어는 확장 후보로 보존하며 근거 없이 폐기하거나 팀 확정으로 표시하지 않습니다.
